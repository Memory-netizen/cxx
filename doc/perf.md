# cxx 的速度与内存评估（对 gcc / clang，真实项目源码）

工具：`doc/speed.sh`（可复现），原始输出：`doc/perf-results.txt`，汇总：`doc/perf-summary.sh`。
机器：8 核 / 7.5 GB，WSL2 Ubuntu，空载（load < 1.3）；gcc 16.0.1（trunk）、clang 23.1.2、cxx 为本仓库 HEAD。

## 1. 方法

把真实开源项目的**翻译单元原样**交给三家编译，命令行用它们**自己构建系统给出的那一份**：
`make -n` 取配方，树已构建时按 `doc/realworld.sh` 的两个回退（无 autoconf 状态用 `make -Bn`，
有则用 `make -n -W <每个 .c>`，因为 `-B` 会让 cpython 重跑 configure）。

只统一掉「测量的是程序而不是编译器」的开关：`-O0`、`-w`，从项目命令行里去掉
`-g`/`-M*`/`-std=`；另给 clang 补 `-std=c2y`、gcc 补 `-std=c23`（cxx 默认即 C2y）。
cxx 不认识的开关由探针逐条探测后剔除并打印（见 §4）——三家最终拿到**同一份命令行**。

两个模式：

| 模式 | 命令 | 含义 |
|---|---|---|
| **fso** | `-fsyntax-only` | 只跑前端：预处理 + 解析 + 折叠（cxx 在此返回，§R118 不生成 IR）。三家唯一可比的一段 |
| **full** | `-c -o /dev/null` | 编译到目标文件。cxx 这条路是：自己的前端 → 输出 LLVM IR → fork clang 把 IR 翻成汇编 → 汇编器 |

一次测量 = `/usr/bin/time` 包一次编译，取 **3 次中最快的一次**（内存取同一次的值，逐次抖动 < 2%）；
时间是墙钟秒，内存是 `/usr/bin/time` 报的**最大 RSS**——三家都是多进程（cc1 + 汇编器），cxx 还多一层 clang。

负载（`~/rw` 下的真实源码，8 个可用 TU）：

| 负载 | 规模 |
|---|---|
| `sqlite/sqlite3.c` | 9.1 MB，约 25 万行（amalgamation） |
| `cpython/{Parser/parser.c, Python/ceval.c, Python/compile.c, Modules/_pickle.c}` | 0.3–1.3 MB，CPython 自己 `make` 的命令行 |
| `tinycc/tccgen.c` | 0.3 MB |
| `zlib/deflate.c`、`lua/lparser.c` | 小文件，用来看固定开销 |

## 3. 结论

**（一）瓶颈全在前端，而且是「大文件才显形」的那一类。**
`-fsyntax-only` 下 cxx 是 gcc 的 **8.4 倍**、clang 的 **4.3 倍**耗时（几何平均）。
按行算更直观：sqlite 的 25 万行，cxx **5.5 万行/秒**，gcc **49 万**，clang **29 万**。
比值随文件增大而变差（小文件 3–5 倍，cpython 的重 TU 12–15 倍，sqlite 9 倍），
说明不是固定开销，而是**随规模增长的那部分**——词法/预处理/符号表这几条每行都要走的路径。

**（二）内存是「clang 量级」，不是「gcc 量级」。**
前端内存 cxx / clang = **1.13×**（几乎持平），而对 gcc 是 **3.05×**。
峰值出现在 sqlite 前端：cxx **349 MB** vs gcc 84 MB vs clang 125 MB（gcc 的前端最省）。
full 模式下三家都涨（后端吃内存），cxx 417 MB、gcc 292 MB、clang 183 MB —— 差距被后端摊薄到 1.65×。

**（三）端到端反而接近，因为后端是 clang 的。**
`-c` 下 cxx 只比 gcc 慢 **2.46×**，比 clang 慢 4.34×（它的前端慢 4.28×，后端与 clang 同一套）。
把两个模式相减可以看出 **IR 往返的代价**：sqlite 上 cxx 的「后端部分」是 9.84 − 4.58 = **5.26 s**，
而 clang 从 IR 到目标文件只用 2.84 − 0.86 = **1.98 s** —— 差在「打印 IR 文本、再让 clang 重新解析」
这条路上，而不是后端本身。

**（四）固定开销约 40 ms。**
最小的负载（zlib 的 deflate.c）上 cxx 0.05 s、gcc 0.01 s、clang 0.03 s：
cxx 的启动比 gcc 贵，与 clang 同量级。对单文件小 TU 这是主要差距来源，对真实项目可忽略。

**（五）cxx 会拒绝真实项目在用的两个开关**：cpython 的命令行里有
`-fno-strict-overflow` 与 `-fvisibility=hidden`，cxx 报 `unknown argument` 拒绝（gcc/clang 都接受）。
探针把这两条**剔除并打印**（剔除不影响前端工作量，不会美化 cxx 的成绩），
但它们决定「项目原样能不能编」——其中 `-fvisibility=hidden` 在真实构建里很常见，值得优先补。

## 4. 限制与没测到的

- **ffmpeg 两个负载三家都编译失败**，因此表中为 `-!`：探针从它的 `make -n` 里取到的配方
  缺少该文件真正需要的 `-I`/`-D`（ffmpeg 的每个目录有自己的 `CFLAGS`，`-W` 回退拿到的是
  另一条配方）。这是探针的限制，不是编译器的结论，补法是把配方按目录过滤后重取。
- **内存是「最大的那个进程」**，不是整棵树的合计。三家都是驱动的形式，口径一致，但
  cxx 的驱动会 fork clang，因此它的数字只反映其中一个进程的峰值。
- 只测了 `-O0`。`-O2` 下后端占比更大，cxx（前端慢、后端与 clang 相同）的相对劣势会缩小；
  但**前端差距不变**，因为 `-O0` 已经把前端孤立出来测过了。
- 未测增量/并行构建、未测 `-g`（调试信息）、未测 LTO。

## 5. 前端瓶颈：parse 占 85%，其中两个函数占 67%

**（一）分段计时**（在 `main.c` 里临时插桩，`CXX_TIME=1` 打印，量完已还原；
sqlite3.c `-fsyntax-only`，`-O2` 构建）：

| 阶段 | 秒 | 占比 |
|---|---|---|
| `tokenize` | 0.13 – 0.17 | ~6% |
| `preprocess` | 0.13 – 0.20 | ~7% |
| `filter_tokens` + `join_adjacent_string_literals` | 0.02 | 1% |
| **`parse`** | **2.08 – 2.14** | **~85%** |
| `fold_ast` | 0.018 | 1% |

tccgen.c 同形：parse 0.260 s / 合计 ~0.33 s（79%），preprocess 0.060 s。
**结论：前端就是解析器，别的阶段都不值得先动**（预处理共 ~13%，折叠可忽略）。

**（二）热点函数**（gprof。两个坑先说清楚：cxx 的驱动会
`fork+exec` 出 `cxx -cc1` **子进程**做前端，所以 profile 属于子进程 —— 要用
`GMON_OUT_PREFIX` 让每个进程各写一份，取最大的那份；另外 clang 的 `-pg` 只装
`mcount` 计数，直方图采样要子进程那份文件里才有）：

| 函数 | self 秒 | 占前端 | 调用次数 | 每次 |
|---|---|---|---|---|
| **`declspecs`** | **1.32** | **41.5%** | 40,842（+2,736 递归） | **~32 µs** |
| **`new_string_literal`** | **0.82** | **25.8%** | 5,113 | **~160 µs** |
| `compound_stmt2` | 0.01 | 29.7%（含子） | 15,127 | |
| `init_decl_list` | 0.02 | 25.4%（含子） | 8,527 | |
| `stmt` | 0.01 | 20.8%（含子） | 48,225 | |
| `primary` | 0.02 | 13.9%（含子） | 191,962 | |
| `tokenize` | 0.07 | 4.3% | 3,055 | |
| `preprocess` | 0.01 | 12.4%（含子） | 1 | |

`parse` 自身 inclusive 86.2%（与分段计时的 85% 相互印证）。
**两个函数吃掉前端的 67%**，而它们每次调用的成本（32 µs / 160 µs）比这两个函数
该有的成本高一到两个数量级 —— 这不是「函数写得慢」，是里面有**随输入规模增长的隐藏工作**
（哈希链探测/重哈希、逐字符循环、重复构造类型之类）。
`-O2` 会内联，所以「self」包含被内联进来的被调者，定位到函数这一层是它的分辨率上限。

## 6. 怎么把它加快：按性价比排序

1. **先用 `-O2` 构建**（`make DEBUG=0`，Makefile 里本来就有）：前端实测快 **1.7–2×**，
   内存**一模一样**。sqlite3.c `-fsyntax-only` 4.17 → 2.44 s，`tokenize+preprocess`
   0.69 → 0.34 s，tccgen 0.40 → 0.32 s，`-c` 5.93 → 5.14 s。
   这一条不需要改一行代码，就把 §2 里「前端比 gcc 慢 8.4×」变成约 4–5×。
   > 注意默认 `make` 是 `DEBUG=1`（`-g -O0`）；上面所有 8 核基准数字都是拿这个 `-O0`
   > 二进制测的，报告已就地说明。
2. **攻 `declspecs`（41%）与 `new_string_literal`（26%）**。方法：继续用 gprof
   （`GMON_OUT_PREFIX` + 子进程那份 `gmon.out`）配合**在函数内部插桩计时**，
   找出那 32 µs / 160 µs 到底花在哪一步。
   这台机器上其它 profiler 的可用性（都已试过，记下来省得重试）：
   `perf` 是残缺安装（提示装 `linux-tools-standard-WSL2`），WSL2 也没有 PMU；
   `valgrind --tool=callgrind` 下 cxx 只执行 ~17 万条指令就退出（不兼容点未查明）；
   `gdb -p` 被 `yama/ptrace_scope=1` 挡住（只能 attach 子进程）。
3. **端到端的下一半**：`-c` 5.14 s − `-fsyntax-only` 2.44 s ≈ **2.7 s 在 IR 往返**
   （打印 IR 文本 → clang 重新解析 → 汇编）。前端修好之后这里就是大头，
   但它是驱动架构的改变（改成库接口/复用同一 clang 进程），要先量后动。
4. **内存 349 MB**（9 MB 输入）：`vnew`/`emalloc` 从不释放（arena 风格，`vnew` 只做几何扩容）。
   改成按阶段可回收的区域分配器能同时降峰值和改善局部性 —— 结构性改动，排在后面。
5. **不要先动的地方**：预处理（~13%）、`filter_tokens`/`join`（1%）、`fold_ast`（1%）。

## 7. `new_string_literal` 的 0.82 s 从哪来：`__func__` 的字符串是**无条件**建的

§5 里 `new_string_literal` 是第二大热点（self 0.82 s，5,113 次调用，~160 µs/次）。
用户的假设是：**每个函数定义都无条件建了一个函数名的字符串字面量**，而这些字符串几乎没人用，
既花了建的时间，又把查重表撑大、拖慢了后续查重。代码印证了这一点 ——
`src/parser.c:9345-9351`，每个函数定义都会：

```c
Type *fn_name = array_of(T.ty_char, str_len(var->id) + 1);
NameSpace *tmp  = push_namespace(scope, id_func,     SYM_VAR, fn_name, var_name);
NameSpace *tmp2 = push_namespace(scope, id_function, SYM_VAR, fn_name, var_name);
NameSpace *tmp3 = push_namespace(scope, id_pretty,   SYM_VAR, fn_name, var_name);
tmp3->var = tmp2->var = tmp->var = new_string_literal(var->id, fn_name);
```

即 `__func__` / `__FUNCTION__` / `__PRETTY_FUNCTION__` 三个名字各挂一份命名空间条目，
**并立刻**建出那个字符串字面量 —— 与函数体里是否出现 `__func__` 无关。

**实测**（`-O2` 构建，在两个调用点加计数、在 `new_string_literal` 内部加计时，
外加一个「跳过该调用」的反事实开关 `CXX_NO_FUNC_STR=1`；两次运行背靠背，比值有效）：

| sqlite3.c | 现状 | `__func__` 惰性（反事实） |
|---|---|---|
| 源码里的真字面量调用 | 2,503 | 2,503 |
| **来自 `__func__` 的调用** | **2,610（51%）** | 0 |
| 表中新建条目 | 3,996 | **1,391** |
| **`new_string_literal` 内部耗时** | **1.572 s** | **0.260 s（−83%）** |
| **`parse` 阶段** | **4.472 s** | **2.565 s（−43%）** |
| tokenize / preprocess | 0.211 / 0.278 | 0.213 / 0.247 |

sqlite3.c 里 **`__func__`/`__FUNCTION__` 的出现次数是 0** —— 这 2,610 次建表纯粹是白做。
tccgen.c 同形但规模小：228/469（49%）来自 `__func__`，新建条目 412 → 184，
内部耗时 0.032 → 0.001 s，`parse` 0.374 → 0.345 s。

**两个可以分开的两点**：

1. **`__func__` 部分是纯浪费，且可惰性化**（预期收益：sqlite3.c 前端 −43% 的 parse 阶段，
   折算到 §2 未经插桩的 2.44 s 前端上约 **−0.9 s**，即前端比 gcc 从 ~4.8× 降到 ~3×）。
   改法很小：9347-9351 只推入命名空间条目、`->var` 留 NULL，并在 `primary()` 解析到
   `__func__` 时按需建（函数名 id 与 `fn_name` 类型在解析函数体前存一份即可），
   ~15 行、无语义变化（标准说 `__func__` 行为「如同声明」，惰性不可观测），
   代价是**不被引用的**那些字符串变量不再出现在 globals 与 `-ast-dump` 里 —— 这本就更合理。
2. **惰性化之后仍有 0.26 s / 2,503 次 ≈ 104 µs 每次**，而 `__func__` 那 2,610 次约
   500 µs 每次 —— 后者几乎每次都走「新建条目」这条贵路径（函数名互不相同，去重不命中）。
   也就是说 `new_string_literal` **自身的新建路径**还有一个独立的、与本次假设无关的问题
   （新建一个 Sym 不该要 0.1–0.5 ms），那是下一个要查的目标。

> 绝对秒数在同一台机器上波动可达 2×（同一次量测的前后两组背靠背比较才有效）；
> 本节的结论都取自同一次运行内的对比。

## 8. 字符串池：把「内容池分家」和「名字按序号打印」分开量

§7 的下一步是「新建 Sym 不该要 0.1–0.5 ms」。把 `intern()` 按三类计数
（标识符 / 字面量内容 / `.str.N` 这类**名字**）、并把 `new_unique_varname()` 的扫描步数与耗时也量出来
（sqlite3.c，`-O2`，`__func__` 已惰性化）：

| sqlite3.c | 调用 | 新建条目 | 桶内探测 | self |
|---|---|---|---|---|
| 标识符 | 514,916 | 24,522 | 1,999,164 | 0.070 s |
| 字面量内容 | 2,145 | 1,301 | 13,889 | 0.001 s |
| **`.str.N` 名字** | **1,381** | **1,381（全部新建）** | 9,102 | 0.002 s |
| 最长桶 | | | 16 条 | |
| **`new_unique_varname`** | **1,503 次** | | **遍历 globals 5,183,142 步** | **0.348 s** |

tccgen.c：标识符 89,149 次 / 0.013 s，字面量内容 265 次 / 0.000 s，`.str.N` 175 次 / 0.000 s，
`new_unique_varname` 186 次遍历 33,730 步 / 0.002 s。

**两个结论，方向相反**：

1. **「内容池分家」的收益很小 —— 这是个反例**。字面量内容那条路径总共 0.001 s、
   13,889 次桶内探测，占全表 199 万次探测的 **0.7%**；标识符那一侧 0.070 s。
   也就是说把字面量内容挪进另一张表，最多省下 1% 量级（真正贵的是标识符自己的量：
   51 万次调用、24,522 个新条目）。**不值得为此改 id 空间与两张表的一致性。**
2. **「名字不格式化、按序号打印」的收益才是那 0.35 s**。`new_unique_varname()`
   为了给每个字符串起一个不重名的名字，**线性遍历整个 `globals` 链表**找同名者 ——
   1,503 次调用走了 **518 万步**（平均每次 3,448 个条目），耗时 **0.348 s ≈ sqlite3 前端 2.49 s 的 14%**；
   而且每个名字还要 `format()` + `intern()`（1,381 个新条目，全是新名字）。
   改成「字符串池按解析顺序编号、名字在打印时按序号给出」之后：
   **去重不再需要唯一性检查**（序号天然唯一）、**不再 format/intern**、
   打印时直接写 `.str.<index>`（保留前导点，形状与今天一致，不引入新的符号绑定问题）。
   实现约 20 行：池里保留内容去重的 `strlit_ht`，另加一个按创建顺序的 `Sym **` 数组，
   名字打印处对 `is_str` 的符号走序号路径。

预期：sqlite3.c 前端再省约 **0.35 s（−14%）**，tccgen 那种规模的文件约 −0.002 s（可忽略）。

### 8b. 匿名记录/匿名复合字面量：能不能也按顺序编号？—— 大半**已经在代码里**

用户的提案：匿名 struct/union 与匿名复合字面量永远不可能被名字引用，所以不必压作用域，
建一个 id 为空的 var，打印时按顺序给出即可；真正有名字的类型与 static 同名变量仍保留 `.N`。
逐条对照代码：

| 类别 | 今天的做法 | 结论 |
|---|---|---|
| 匿名记录（无名 `struct {…}` 与编译器自建记录） | `insert_ty()`：`if (!ty->id \|\| ty->is_anon) name = format("%s.anon.%d", kind, ++anon_seq);` —— **按顺序编号** | **已经是提案的做法** |
| 有名字的类型（重名时） | `else if (i >= 0) name = format("%s.%s.%d", kind, str(ty->id), i);` | 与提案一致（保留 `.N`） |
| 编译器临时量（原子暂存、范围暂存、内建实参临时量…） | `new_lvar(id_anon, …)`，`id_anon = intern("", 0)`，**只挂进 `locals`、不 push 作用域** | **已经是提案的做法** |
| **块作用域的**匿名复合字面量 | 同上，走 `id_anon` | 已经是 |
| **文件作用域 / `static` 的**复合字面量 | `new_unique_varname(intern(".compoundliteral", 16))`（`parser.c:4429`） | **仍是唯一一处**（见下） |
| 字符串字面量 | `new_unique_varname(intern(".str", 4))`（1,381 次 / sqlite3） | 即 §R127b 要改的那 92% |
| 块内 `static` 局部（用户可见的名字） | `format("%s.%s", cur_fn->id, str(id))` 再查重 | 提案说保留 `.N`，同意（且这类很少） |

`insert_ty()` 里那段注释正好是这次要引以为戒的先例：匿名记录的名字**必须只有一个计数器**——
早先两种情况各自计数、都从 `anon.1` 开始，于是两个无关的结构都叫 `%struct.anon.1`，
LLVM 以 redefinition 拒绝整个模块（`libavcodec/jpegxl_parser.c`）。
所以若要给 `.str` / `.compoundliteral` 改按序号打印，规则应当是：

1. **每种前缀一个全局序号**（首次创建时分配），不是每个文件、每个作用域各一个；
2. **序号分配在「内容去重的那个对象」上**：相同字面量仍共享一个对象（cxx 现在就这么做，
   gcc/clang 也是），否则会退化成每个字面量一个全局，IR 反而变大；
3. **打印形状保持不变**（`.str.<i>`、`.compoundliteral.<i>`），避免动符号绑定与可读性。

文件作用域的复合字面量为什么当初要查重：`parser.c:4429` 的注释记着——两个翻译单元各有一个
文件作用域复合字面量时会同时定义 `.compoundliteral`，链接失败（cxx 当年因此链接不了自己）。
但那是**跨 TU** 的问题（靠 local binding 解决），**同一个 TU 内按序号编号就够**。

**收益**（sqlite3.c，`-O2`）：`new_unique_varname` 的 0.348 s 中，`.str` 占 1,381/1,503 次
（≈0.32 s），文件作用域复合字面量等其它约 120 次（≈0.03 s，1%）。
也就是说**匿名记录/临时量这一侧已经没有可省的开销**（它们本来就不经过取名路径），
剩下要做的和 §R127b 是**同一件事**：把「编译器生成的符号按序号打印」这条规则用到
`.str` 与 `.compoundliteral` 上，预计 sqlite3 前端再 **−14%**，同时把
`new_unique_varname` 留给真正有名字的块内 `static`。

顺带记一处同类隐患：`insert_ty()` 自己的 `while (t) { if (t->id == ty->id) i++; t = t->next; }`
是对 `types` 链表的线性扫描（类型数远小于全局数，现在不显眼），改成每个 id 一个计数即可，
与上面第 1 条是同一个做法。

### 8c. 序号化命名已落地，`insert_ty` 也按用户的做法提前退出

实现（`src/parser.c`，在 §R127 惰性 `__func__` 之上 +39/−7）：

- `generated_name(prefix, seq)`：**每个前缀一个序号**。第一个保持无后缀的裸名、其后 `.1`、`.2`…
  —— 与原来 `new_unique_varname()` 的输出**逐个字符相同**（见下面的汇编 diff），但不再遍历 globals。
- `.str` 与 `.compoundliteral` 改走它；`new_unique_varname()` 只留给块内 `static` 局部
  （用户可见的名字，量小且语义上确实需要查重）。
- `insert_ty()`：不再数完整条 `types` 链，而是**取链表上第一个同 id 的条目**（链表是新的在前，
  所以它就是最近的一次），从其名字的后缀读出序号继续 —— 即用户提的做法。

验收：

| `make test` | exit 0；conformance **325 / 0**、c2y 101 / 0 |
| bootstrap | **cxx2 = cxx3 = cxx4 逐字节相同**，21/21 目标文件 |

| A/B（都 `-O2`，同一次运行） | sqlite3 `-fsyntax-only` 2.48 → **2.15 s（−13.3%）**；tccgen 0.47 → 0.45（−4.2%）；lua 0.06 → 0.05（−16.6%）；`-c` 各行在噪声内（±5%） |

### 8d. `attr_lookup` 与 `is_builtin_fn`：改了，但量出来它们本来就不贵

按用户的两条思路改完并量了，**结论是收益很小** —— 有价值的地方在于它把 §R125 里
「`declspecs` 41%」的嫌疑排除掉了一个。

改动：

- **`attr_lookup()` 改按 interned id 比较**：原来每行都 `strlen()` + `strncmp()`（30 行 × 每次查找），
  现在每行一个 id 比较；`__name__` 归一化保留（glibc 头文件就这么写），但只在查表前
  `intern()` 一次（多一个表项，正如用户所说，内存不在这一处）。
- **`is_builtin_fn()` 两道字符快速失败**：`s[0] != '_' || (s[1] != '_' && 非大写)` → 直接返回。
  它在 `primary()` 里对**每个表达式里的每个标识符**调用一次，原来要扫
  30（`builtin_defs`）+ 29（aliases）+ 6（sync）共 65 行。`str(id)` 是直接索引，不是查找。
  已核对：三张表 65 个名字**全部**以 `__` 或 `_` + 大写开头，快速失败不会漏掉任何一个
  （构建期的行数校验 `check_builtin_rows()` 仍然在）。

A/B（都 `-O2`，同一脚本内背靠背，四次取最快）：

| 负载 | 改前 | 改后 | 变化 |
|---|---|---|---|
| sqlite3.c `-fsyntax-only` | 2.77 s | 2.75 s | **−0.7%** |
| tccgen.c `-fsyntax-only` | 0.46 s | 0.45 s | **−2.1%** |
| lua/lparser.c `-fsyntax-only` | 0.05 s | 0.05 s | 0 |

`make test` exit 0（conformance 325 / 0、c2y 101 / 0）、bootstrap **逐字节相同** + 21/21 对象、
tcctests 106 ok / 0 failed —— 改动免费且无回归。

**为什么这么小**：`attr_lookup` 只在真有 `__attribute__` 的地方被调用（sqlite3.c 里不多）；
`is_builtin_fn` 虽在热路径上，但 65 行 id 比较本身只有百纳秒量级，快速失败省下的那部分
在 2.75 s 里就是 1–2%。两条改动都保留（更省、语义不变），但**不能指望它们解决前端**。

**顺带排除一个嫌疑**：`declspecs` 那段 1.32 s 的 self 时间里**不包含** `attr_lookup` ——
`attr.c` 是独立编译单元，不会被内联进 `declspecs`，所以 gprof 把它的时间算在它自己名下，
而这里量出它很小。`declspecs` 每次调用 32 µs 的开销因此另有来源，是下一轮要查的目标
（嫌疑：`is_typename` / `find_typedef` / 限定符与类型说明符的处理循环）。

**顺便记下工具链的教训**（这次花了不少时间）：往 `src/*.c` 里插桩时，把计数器/析构打印
写在**同一个文件**里、并避免用 `%`-format 拼字符串；`edit` 工具无法写 `\\wsl$` 路径，
改动要走 WSL 里的脚本文件。`attr.c` 不认识 `intern()`，需要一行原型。

### 8e. 全部 `strcmp` / `strncmp` / `memcmp` 清点：热路径已经是 id 比较，剩下的是冷的或必须的

用户提出：所有 `strcmp`/`strncmp` 都可疑 —— 已经在哈希去重的符号上再比全量字符串是浪费。
全仓清点（`src/`，139 处）：

| 文件 | 处数 | 是什么 | 判定 |
|---|---|---|---|
| `main.c` | 97 | 命令行选项解析（`-o`、`-E`、`-I`、`-D`…） | **冷**：每次进程一次 |
| `parser.c` | 30 | 约 25 处 `strcmp(a->info->name, "packed"/"aligned"/…)`：比的是**静态表行的名字**；其余 2 处是 `strncmp(intrinsic, "llvm.", 5)`、1 处 asm 操作数表比名字 | **冷**：按属性出现次数跑，且 `a->info` 本就指向 `attrs[]` 的行，指针即可作身份 |
| `attr.c` | 3 | `ns_of()` 的 `"gnu"`/`"clang"`；表内名字 `intern` | 冷（§8d 量到整类 ≈0.7%） |
| `util.c` | 4 | **interning 表自己的 `memcmp`（哈希命中必须用字节确认，不能删）**、日志级别解析、`Int128` 结构比较（不是字符串） | **必须 / 冷 / 不是字符串** |
| `dumpir.c` | 2 | IR 打印器的按名字线性查表 | 冷：调试路径，不在编译路径上 |
| `lexer.c` | 1 | BOM `memcmp` | 每文件一次 |
| `irgen.c` / `preprocess.c` | 2 | `strncmp(intrinsic, "llvm.", 5)` 常量前缀 | 微 |

**关键一条：热路径上的标识符比较已经是 id 比较**，逐一核对过：

- 关键字：`for (…) if (tok->id == kw[i].id)` —— 整数比较，没有字符串比较（`lexer.c` 全文只有 BOM 一处 `memcmp`）；
- 内建函数：§R129 起是两道字符快速失败 + id 表；
- 属性：§R129 起查表按 id，命中后剩下的 `a->info->name` 比较是「表行 vs 字面量」；
- 作用域/宏/字符串字面量：走 hashmap 与 interned id。

所以结论是：**用户的方向对，但这批比较现在要么冷、要么必须有**；这与 §8d 的独立测量一致
（`attr_lookup` + `is_builtin_fn` 合计只有 −0.7% / −2.1%，说明这一族不是前端 2.15 s 的去处）。

**可做但不必做（清洁性，收益≈0）**：给 `attrs[]` 的行一个枚举/指针身份，把那 ~25 处
`strcmp(a->info->name, …)` 改成行指针比较；`ns_of()` 改成传枚举；`irgen` 的 `"llvm."` 前缀
在表初始化时预计算一个 flag。三件都是机械改动、语义不变，且都会让「再比一次字符串」这类
问题绝迹 —— 但按现有测量，它们不会让前端更快。

### 8f. `find_ident` 在作用域名字链表上线性扫描：sqlite3 一次编译 **7970 万步**

按用户指向的路径（`case TK_IDENT` → `find_typedef` → `find_ident`）加了计数器
（`-O2`，`CXX_TIME=1`）：

| | sqlite3.c | tccgen.c |
|---|---|---|
| `is_typename` 调用 | 224,070 | 30,982 |
| `find_typedef` 调用 | 190,417 | 20,706 |
| `find_ident` 调用 | 211,052 | 27,527 |
| 其中未命中 | 30,901 | 11,906 |
| 走过的作用域层数 | 716,787 | 84,087 |
| **名字链表步数** | **79,715,113** | **25,365,768** |
| 平均每次调用 | **378 步** | **921 步** |
| 该次 `-fsyntax-only` 总时间 | 2.83 s | 0.42 s |

原因是 `find_ident()` 在**每个作用域**里都做：

```c
NameSpace *hit = NULL;
if (sc->ht)
    for (NameSpace *ns = sc->ht[tok->id & (sc->ht_cap - 1)]; ns; ns = ns->hnext)
        if (tok->id == ns->id) { hit = ns; break; }     // 哈希桶先找一个
for (NameSpace *ns = hit ?: sc->vars; ns; ns = ns->next)   // 再从那里顺着 vars 链扫
    if (tok->id == ns->id) { ... }
```

第二段是**对作用域全部名字的线性扫描**（未命中时从 `sc->vars` 头开始 ⇒ 走完整条链），
而 `is_typename()` 在每个有歧义的标识符位置上被调用，绝大多数答案是「不是类型名」。
80M 步 ×（一次简单的指针追逐 + 一次 id 比较，很可能还带 cache miss）≈ **0.1–0.8 s**，
即 sqlite3 前端 2.83 s 的 **4–28%**。这就是 §R125 里 `declspecs` 每次 32 µs 的真身。

**评估：用户的方案（为类型名单列一张表快速判断 ident 是否是类型）确实有改善，而且不止一处收益。**

1. **`is_typename()` 的快速否定**：维护一份「当前作用域链里存在的 typedef 名 id」集合
   （哈希集合；typedef 声明时插入、其作用域退出时删除 —— cxx 的作用域是整块释放的，
   所以需要在作用域里记一份「本层插入过的 typedef id」列表以便退出时撤销）。
   集合里没有 → 直接回答「不是类型名」，**整条作用域链与 vars 扫描全部省掉**。
   绝大多数标识符（局部变量、函数名、成员名）都不在这张表里，命中率天然高。
2. **更根本的一处（顺带发现）**：`find_ident()` 的第二段扫描本身就是多余的 ——
   哈希桶 `hnext` 链里已经含有同名的全部声明（插入时每次都会挂上），
   所以按「最新在前」遍历**桶链**即可，不必再去走 `sc->vars`。
   这一改动同时覆盖 `is_typename` 之外的所有 `find_ident` 调用者
   （`primary()` 的 `case TK_IDENT`、声明解析、`extern` 链接检查等），收益比 ①更大。
   代价是顺序语义要小心核对：`is_extern` 分支要按「最近一次声明」判断链接，
   而桶链的新在前顺序正好给出这个次序。

**验证方式（下一轮做）**：① 与 ② 分别做 A/B（都 `-O2`，同一次运行内前后对照），
并用 `make test`（conformance 325 / 0）、bootstrap 逐字节、tcctests 106 / 0 三条守住语义。
本节只做定量评估与定位，未改代码。

### 8g. `find_ident` 改走哈希桶：sqlite3 前端 **1.53 → 0.48 s**，全部输出不变

按 §8f 的方案 ② 实现（`src/parser.c` 的 `find_ident()`）：不再沿 `sc->vars` 扫作用域全部名字，
改为遍历该名字的哈希桶链。等价性由代码本身保证 —— `push_namespace()` 把每个名字**同时**挂进
`vars` 与 `ht[h]` 两条链，都是**最新在前**，rehash 也按注释明确保持该顺序；所以桶链里
同名的相对次序与 `vars` 链完全一致，只是不再经过无关的名字。

A/B（都 `-O2`，同一次运行内前后对照）：

| 负载 | 改前 | 改后 | 变化 |
|---|---|---|---|
| sqlite3.c `-fsyntax-only` | 1.53 s | **0.48 s** | **−68.6%** |
| tccgen.c `-fsyntax-only` | 0.33 s | **0.09 s** | **−72.7%** |
| lua/lparser.c `-fsyntax-only` | 0.04 s | 0.03 s | −25.0% |

三道闸全绿：`make test` exit 0（conformance **325 / 0**、c2y 101 / 0）、bootstrap
**cxx2 = cxx3 = cxx4 逐字节相同** + 21/21 目标文件、tcctests 106 / 0；
另外用一个含 typedef、**内层同名 typedef 遮蔽**、属性、`__func__`、字面量、复合字面量的
用例比对 `-S` 输出：**逐字节相同**。

**①（typedef 名快速否定）评估结论：不需要了。** 桶遍历之后 `find_ident` 每次只走
1–3 步（原来是 378 步），`is_typename` 这条路径已经不构成瓶颈；再叠一层 typedef 集合
只会多一处需要维护撤销逻辑的状态。**不做。**

|---|---|---|---|---|
| sqlite3.c | `-fsyntax-only` | 0.49 | 0.97 | **0.65** |
| tccgen.c | `-fsyntax-only` | 0.10 | 0.15 | **0.11** |

这一轮优化的累计（同一台机器上各次 A/B 的乘积，均为 `-O2`、输出逐字节不变）：

已随桶遍历消失，需要重新取一份 profile）。

### 8i. 现在的瓶颈评估：**IR 往返**占了 `-c` 的约三分之二

`cxx -###` 给出的 `-c` 流水线（sqlite3.c）：

```
cxx -cc1 … -cc1-input sqlite3.c -cc1-output /tmp/cxx-XXXX        # 前端 → IR 文本
clang -target x86_64-linux-gnu -S … -x ir /tmp/cxx-XXXX -o /tmp/cxx-YYYY   # IR → 汇编
clang -target x86_64-linux-gnu -x assembler -c /tmp/cxx-YYYY -o out.o     # 汇编 → 目标文件
```

**3 个进程、2 个临时文件**，而且第二个 clang 只当汇编器用。

分段计时（`-O2`，sqlite3.c，best of 3，`-O0`）：

| 阶段 | 秒 | 占 `-c` |
|---|---|---|
| `-fsyntax-only`（纯前端） | **0.58** | 18% |
| `-S`（前端 + irgen + 打印 IR + clang: IR→汇编） | 2.65 | 84% |
| `-c`（再加汇编器那一步） | 3.17 | 100% |
| clang 自己 `-S` 同一份 C | 2.20 | — |
| clang 自己 `-c` 同一份 C | 2.02 | — |
| gcc `-c` 同一份 C | 5.16 | — |

（`-emit-llvm` 那一项在本环境量不稳 —— 它把 IR 写到 `/tmp`，而这里 `/tmp` 会被清空；
结论只用上面三项。）

**读法**：

1. **前端已经不是瓶颈**：0.58 s，只占 `-c` 的 18%，而且比 clang 自己的前端（0.94 s）还快。
2. **IR 往返 ≈ 2.1 s（约 65%）**：`-S` 减前端 = 2.07 s，这一段是「cxx 生成并打印 IR 文本 +
   clang 重新解析这份文本 + 代码生成」；而 clang 从 C 直接做同样的后端工作只要
   2.20 − 0.94 = **1.26 s**。也就是说**同一次代码生成，走文本 IR 比走 clang 自己的 AST 多花约 0.8 s**。
3. **多出来的汇编器进程 ≈ 0.5 s**：`-c` − `-S` = 0.52 s，这是第二次 `clang -x assembler -c`
   加上一个临时文件往返。
4. 合起来：cxx 的 3.17 s 对 clang 的 2.02 s（1.57×），而 **cxx 的前端本来比 clang 快 0.36 s** ——
   如果后端不绕这一圈，理论上应落在约 1.7 s，**比 clang 自己还快**。

**建议（按实测收益/代价排序，均未做）**：

| 做法 | 预期收益 | 代价 |
|---|---|---|
| 把「IR→汇编→目标文件」合成一次 `clang -x ir … -c -o out.o`（用 clang 的集成汇编器），`-S` 另走一条路 | 省掉一个进程 + 一个临时文件往返，sqlite3 上约 0.1–0.3 s | 驱动改动约 10 行 |
| 用管道把 IR 直接喂给 clang（`-x ir -`），省掉 `.ll` 临时文件 | 一个文件的写+读 | 同上，很小 |
| **真正去掉往返**：让 cxx 通过 LLVM 的 API 建模块（而不是打印文本再让 clang 解析） | **约 0.8–1.1 s/TU**，落点约 1.7 s（快过 clang 自己） | 驱动架构改动：cxx 要链接 LLVM 库，属新阶段的工作，先量后动 |
| 前端再挖 | 剩余 0.58 s，占比 18% | 需重新取一份 profile（`declspecs` 的 32 µs 已随 §R132 消失） |

另外记一条工程性的观察：每个翻译单元 3 个进程、2 个临时文件，意味着**并行构建时**（`make -j`）
每个 TU 的进程数与临时文件 I/O 都会翻倍放大 —— 这也是「合并成一次 clang」的另一个理由。

### 8l. `Sym` 的函数专有尾部：结构上成立，收益上不成立（1.5 MB / 348 MB = 0.4%）

用户提出：`struct Sym` 为所有符号都保留了 11 个只有函数才用的字段（`funcspec`、`body`、`labels`、
`locals`、`start`、`end`、`num_blk`、`num_lbl`、`blks`、`num_indirectbr`、`indirectbr`），
而函数符号远少于变量符号；把这段封装成单独结构、`Sym` 里只留一个指针如何？

**实测**（sqlite3.c `-fsyntax-only`，`-O2`，峰值 RSS 356,728 KB）：

| | 值 |
|---|---|
| `sizeof(Sym)` | **224 字节** |
| 函数专有尾部（`offsetof(Sym, funcspec)` 之后） | **80 字节 = 35%** |
| 分配的 `Sym` 总数 | **26,360** |
| 其中函数 | 4,935（**18.7%**） |
| **全部 `Sym` 占用的字节** | **5.9 MB = 峰值的 1.7%** |
| 整段尾部的总开销 | 2.0 MB |
| **移出尾部可省**（(总数−函数数) × (80−8)） | **1.5 MB = 峰值的 0.4%** |

tccgen.c 同形但更小：7,552 个 `Sym`= 1.6 MB，可省 0.3 MB。

**结论：方案的形状对（224 字节里确实有 80 字节只有函数用），但人口太小 —— 全部 `Sym` 只占峰值
的 1.7%，真正能省下的 0.4% 不值得动。** 附带的速度论据也很弱：结构从 224 缩到 152 字节确实
更紧凑，但 26,360 个符号一共 5.9 MB，本来就在 L3 里，量不出差别。
风险面却不小：这 11 个字段的读写点分布在整个 parser/irgen/dumpast（机械但面广），
而且要在「符号变成函数时」惰性分配那半个结构（`sym->fn` 按需创建），一旦漏判就是空指针。

**真正的大头在哪**（本轮未量完，按已知量估算，下一步用分配器直方图确认）：sqlite3 的 9.1 MB /
25 万行预计产生 300–500 万个 token 与 100–200 万个 AST 节点，而 `Token` 与 `Node` 都从
**永不释放的 arena** 分配 —— 仅这两类就是数百 MB 量级，`Sym`（5.9 MB）、intern 表（约 1 MB）、
`NameSpace`（约 1.3 MB）都只占零头。
所以内存的方向不是「缩小结构体」，而是**按阶段回收**：token 在 `parse()` 之后即死
（§R118 的流水线里 `-fsyntax-only` 正好在那里结束），把 token 与 AST 放进两个可分阶段释放的
区域，峰值才可能实质下降。

（本轮想把分配器按尺寸直方图统计出来，插桩匹配 `emalloc` 函数签名时失败，已还原；
下一轮用正确签名重做即可得到确切分布。）

### 8n. 内存池 + `Loc` 方案评估的结论（细节见计划 §R138）

改动面实测比设想集中：读取 token 的站点 175 处（parser 111、type.c 31、preprocess 13、dumpast 3），
诊断调用 494 处，但**跨过「释放 token 池」这一点之后仍需 token 的只有约 35–40 处**
（type.c 的 31 处加 parser 尾部；`irgen.c` 一处都不读 token，它的诊断全是 `fatal()`）。
因此：**释放点定在 `fold_ast` 之后**（不是 `parse` 之后）、**`Loc` 只覆盖跨释放点的路径**、
**池子只要 3 个**（永不释放 / token / node+type；「预处理池」多余，那 93 MB 就是 token 副本）。
先做零风险的 `Token` 压缩（约 50 → 36 字节，−38 MB），再做生命周期改造
（fso 峰值 345 → 约 115 MB，`-c` 412 → 约 181 MB）；安全网是 **ASan 构建的 cxx** 跑全套闸门 ——
这一改动的失败模式正是 use-after-free，而 valgrind 在本机跑不了 cxx（实测）。

### 8o. `sizeof(Token)` 实测 64 字节：位域打包是无效的（修正 §8n 的第一步估算）

| | 值 |
|---|---|
| `sizeof(Token)` / `_Alignof` | **64 / 8** |
| 布局 | `next` 8、`origin` 8、值 union 16、`file` 8、`loc`/`len`/`filename`/`line_delta` 16、尾部小字段 6 → 62 → 补齐 64 |
| 尾部 | `{uint16_t lit_suffix \| uint8_t enc_prefix}` 2 + `kind` 1 + 3 `bool` 3 = 6 |

尾部从 6 压到 4 只省 2 字节，62→60 按 8 字节对齐**仍是 64** —— 所以要变小必须一次减 ≥8：
候选是 `file` 指针→`file_no`（4，另需尾部打包凑 6 ✗ 还差 2）、`origin`→`Loc` 链（8）、
值 union 移出（16）。因此**把①并入③**：先用 `Loc` 换掉 `origin`、把 `file` 换成 `file_no`，
`Token` 由 64 降到约 48（−25%，约 34 MB），叠加在「`fold_ast` 之后释放 token 池」
（fso 345→约 115 MB）之上。②（`Loc` 类型与转换点）成为第一个真正的动作。

### 8p. `SrcFile::id` 是显示名的 id，不是文件唯一键（slice 2 撤回）

`new_file()` 里 `file->id = intern(name, strlen(name))` —— 那是**显示名**的 interned id：
同名文件共享同一个值，而 `#line` 还会把显示名与真实文件分开（`tok->filename = display_name`、
`tok->file = cur_file`）。所以 `Loc` 不能拿它当文件键，两个字段（显示名 / 文件）都必须留。
slice 2 的自包含 `Loc`（20 字节、按 id 查表）已**还原**，tree 回到 slice 1 + 合并 clang 的状态，
`make test` 325 / 0。修正方案：给 `SrcFile` 加一个新的唯一 uid + 按 uid 建表，
再逐处改掉 `tok->file` 的 28 个读者，最后去掉 `Token.file` 并把尾部打包 —— 64 → 56 字节，约 −21 MB。

### 8q. 诊断已经全部走 `Loc` 路径（slice 2 完成）

`SrcFile` 得到唯一 `uid`（与显示名 id 分开，因为 `#line` 会把两者拉开），`Loc` 变成 20 字节的自包含值
（`sizeof(Loc) == 20`，实测），`diag()`/`diag_exit()` 的本体改为 `loc_of()` + `emit_diag_loc()` ——
于是**每一条诊断**都在跑新路径。验收：`make test` 325 / 0、bootstrap **逐字节相同 + 21/21 对象**、
tcctests 106 / 0；三类消息逐字不变，其中 `#line 100 "other.c"` 报 `other.c:100:25` 正是
「显示名 ≠ 物理文件」的那一类。剩下的是 slice 3：改掉 `tok->file` 的 28 处读者并删掉该字段
（−6 字节/记号 ≈ −21 MB），再进入③（释放 token 池，−230 MB）。

### 8r. `Token` 64 → 56 字节（slice 3），但峰值 RSS 没动 —— 并修正 §8m 的一处口径

slice 3：`Token.file`（8 字节指针）→ `file_uid`（4 字节，配 `file_of()` 内联访问器与 lexer.c 的文件表），
尾部 6 字节打包成 4（`lit_suffix` 2 + `kind` 1 + `enc_prefix:4`/三个 `bool:1` 1），
写者读者全数转换。**`sizeof(Token)` = 56**（改前 64）；`make test` 325 / 0、bootstrap **逐字节相同 + 21/21 对象**、
tcctests 106 / 0；sqlite3 `-fsyntax-only` 峰值 **356,772 KB**，与改前记录的 356,600 KB 无差异 ✗。

原因是我预期的基数错了：§8m 的「Token 137.1 MB / 2,709,107 次」来自按结构打点的插桩，而那次
**`mem_tag` 置位后从不清零**，后续分配都被算进最后一个 tag —— 所以那个数是**上界**。
§8m 的**阶段**分布不受影响（按阶段边界记账）：tokens 230.3 MB、parse 114.9 MB，仍然成立。
下一步：用只计数、不改 tag 的探针量出真实 Token 数量与字节数，再定③（释放 token 池）的收益。

### 8s. dumptok/dumpast 的时机检查：③ 的改动面因此小一个数量级

流水线（main.c）：`dump_raw_tokens`(1017) 与 `dump_tokens`(1021) 在 `parse` 之前；
**`dump_ast`(1041) 在 `parse` 之后、`fold_ast`(1043) 之前**；`irgen`(1052) 一处都不读 token。
token 读者的完整人口：parser 111、**opt_ast 17**（`fold_ast` 就定义在 `opt_ast.c:905`）、
preprocess 13、dumpast 3 —— **全部在 `fold_ast` 之前**。
所以把释放点定在 `fold_ast` 之后，**没有任何读者在释放之后运行**：③ 不需要转换诊断，
只需「给 token 单独开池 + 在 `fold_ast` 后释放 + 验证」。三条硬约束要记住：
`dump_ast` 必须留在 `fold_ast` 前、`-fsyntax-only` 的返回前要释放、`irgen`/`dumpir` 的诊断不得读 token。

### 8t. callgrind 可用（更正），优化①：`dumpir` 按 id 查重 —— tccgen 指令数 −13.8%

**工具更正**：valgrind 在这台 WSL 上可用，正确姿势是直接 profile cc1 进程
（`valgrind --tool=callgrind ./cxx -cc1 -cc1-input <src> -cc1-output /tmp/x.ll`）；
我此前 profile 的是会 fork 的驱动，所以只看到几个函数。**按结构插桩那套易错手段可以退休。**

tccgen 的 cc1（914,592,386 条指令）里 **`__strcmp_avx2` 占 12.28%**，来自 `dumpir.c` 的
`already_emitted`/`name_is_defined` 两处按名线性查重 —— 比的是 `str(sym->id)` 这种**已经
interned 的字符串**，与 `find_ident` 同病；而 `dumpir` 是每次 `-c`/`-S` 都跑的 IR 打印器，
不是调试路径（我上一轮的判断有误）。

改成 `emitted_id(sym)` + 两张 `{uint32_t id}` 表之后：**914,592,386 → 788,204,173（−13.8%）**，
`__strcmp_avx2` 从热点榜消失；`make test` 325 / 0、bootstrap **逐字节相同 + 21/21 对象**（IR 文本未变）、
tcctests 106 / 0。新的热点榜与各自的方向见计划 §R144。
