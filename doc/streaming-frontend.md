# 拉取式前端：主张评估与重构计划

设计阶段文档，不含实现。评估对象：把"**整文件词法化 → 整条流物化 → parser 遍历**"改成
"**parser 驱动、token 按需产出**"（parser 调 `next_tok()`/`lookahead(N)`，预处理器调
`next_rawtok()`，词法器按需产出，预处理层负责前瞻/回退）。

实测依据在 `doc/perf.md` §8cl（四个编译器的分相/指令数/缓存）与 §8cm（死区普查与收益推算）。

---

## 0. 摘要

1. **方向成立**，而且与现有代码的落差比看起来小：`#include` 今天**已经是输入栈** ——
   `include_file()`（preprocess.c:1882）用 `*rest = tok2` 把被包含文件的链接进流，
   `push_file()`/`pop_file()`（176/199）记回程；`preprocess2` 的段循环本身就是段级流。
   真正批量的只有两处：**单文件全量词法**、**"预处理器把整条流物化后才交给 parser"**。
2. **"按需读入文件"要放弃**：`Token` 不存拼写，只存 `(file_uid, loc)`，文字由
   `tok_text()` 现算（cxx.h:600 `file_of(uid)->contents + loc`）。字节层必须**常驻**，
   惰性属于**记号层**。滑窗字节缓冲会同时打断宏展开的 stringize/paste 与 parse 期的诊断。
3. 收益（§8cm 推算）：前端约 **−4% ~ −10%（最可能 ~6%）**，`cxx -c` 端到端
   **−1.3% ~ −3%**；**内存是确定收益**（死区记号占预处理输入 39.4%，arena 117 MB 中
   31.6 MB 是死区）。真正的大头不在前端：`cxx -c sqlite3` 里 cc1 只占 32%，cc1 里
   IR 打印占 36%。
4. 你的七条主张里，**五条成立、一条要限范围、一条要换形式**（详见 §3）。

---

## 1. 目标与非目标

**目标**

* 内存：token 工作集从"整条流 + 整份宏展开中间物"降到"前瞻窗口 + 当前展开"。
* 让 `-E`/`-M` 可以边产边打（今天要物化 125 MB 才打印）。
* 为将来的增量/IDE 用法留出接口（只解析到某个声明）。

**非目标**

* 不为速度做这件事（§8cl：10× 的差距在后端，不在前端）。
* 不重写宏展开引擎的语义；不改 parser 的函数形态（95 个 `Token **rest` 出参保持）。

---

## 2. 三层与不变量

| 层 | 组件 | 不变量 |
|---|---|---|
| **L1 字节层** | `read_file()`（lexer.c:1181）、`SrcFile`（cxx.h:339） | **整份内容常驻且地址稳定**（`mmap` 或一次性读入后永不释放）；`line_offsets` 只增不减 |
| **L2 记号层** | `next_rawtok` / 展开栈 / 输出层 | 记号按需产出；**输入栈四类源**；已产出尾巴可**撤回**；宏展开仍以"每次展开物化小表"为单位 |
| **L3 parser** | `parser.c`（9,906 行，95 个 `rest` 出参） | 游标是**数据**（`tok`/`rest`），不是全局状态；缓冲**可回退**，但**不做 pp 状态快照** |

## 3. 逐条评估你的主张

### 3.1 `tok_text()` 的字节常驻

**事实**：36 行 / 37 次调用，分布与冷热：

| 位置 | 次数 | 冷热 | 备注 |
|---|---|---|---|
| lexer.c:58 `skip()` 报错 | 1 | 冷（词法期） | |
| lexer.c:462 `convert_universal_chars` | 1 | 热（含 `\u` 时） | 就地 |
| lexer.c:511/513 `convert_char_literal` | 2 | **热**（每个字符常量） | 就地 |
| lexer.c:601/602 `convert_pp_num` | 2 | **热**（每个 pp-number） | 就地 |
| preprocess.c:923/945/955 `join_tokens`/`join_spelling` | 3 | **热**（stringize `#`） | 读 `read_macro_args` 收集的实参记号 |
| preprocess.c:994 `paste` | 2 | **热**（`##`） | 同上 |
| main.c:872/873/888/922 `needs_space`/`print_tokens` | 4 | 热（仅 `-E`） | |
| parser.c 7 处 + type.c 4 处 | 11 | 冷（全是 error/warning） | 读 `Node.tok`/`Type.name`/`ty->name` 里的记号 |
| preprocess.c:605/1431/1715/1766/1843/1921/1928 | 7 | 冷（`#if` 报错、`#include` 名、`#pragma pack`、`#line`） | |
| dumpast.c:209/210、dumptok.c:78/100 | 4 | 冷（`-ast-dump`/`-dump-tokens`） | |

**判定：一半成立。**

* **成立**："热路径上文字就在当前缓冲区里" —— lexer 内部那 6 处确实就地（转换与报错都发生在
  扫描位置），stringize/paste 也发生在同一次展开内。
* **已修正**（见 `doc/perf.md` §8cn）：`-E` 与 `#line` **不是**"很久以后"的读者 ——
  `-E` 完全可以边产边打（实测 gcc/clang/tcc 在诊断之前已交出 106~109 KB，cxx 是 **0 B**），
  `#line` 读的也是刚 `read_line()` 读进来的那一行。这两条从"字节必须常驻"的理由里去掉。
* **仍然不成立**的部分，真正的理由是**宏体借用了别的文件的文字**：
  1. `#define` 把宏体存成记号链，记号的 `(file_uid, loc)` 指向**定义它那个文件**。宏可以在
     几千行之后、甚至从另一个文件里展开，此时 `#`/`##`（`join_tokens` 923/945/955、
     `paste` 994）与 `-ast-dump`/诊断仍要读那份文字 —— 而那个文件在逻辑上**早就 include
     结束了**。滑窗一旦重置指针，这里必崩，且崩的距离没有常数上界（实参可以任意长）；
  2. parser/type 那 11 处虽然是冷路径，读的却是**长期存活结构里的记号**
     （`Node.tok`、`Type.name`、`Sym.tok`、`Member.tok`），问题不是"文字还在不在缓冲区"，
     而是**记号对象本身还在不在**（这是 `Loc` 存在的原因，cxx.h:551-562）。
* **结论**：`next_c` 的"缓冲区空则 `read` 进来、重置指针"应改为
  **在 mmap 视图上推进指针**（不重置）；惰性只放在记号层。
* **另一条可选路线（记录在案，不推荐）**：让宏体**自己拥有拼写**（tcc 的 `TokenString`
  做法：`#define` 时把体复制一份文字），这样文件字节原则上可以释放。代价是每个体记号一次
  定义期复制，且 `Loc` 的语义要跟着改（`Loc` 只有 `(file_uid, loc)`，文字没了它就报不出
  源码行）—— 为了省几个 MB 去动 20 字节的 `Loc` 与全部诊断，不划算。
* 顺带一句：`Token` 带 `loc`/`len` 并不是"因为非流式"，而是"诊断要能定位到一个比记号池
  活得久的位置" —— `Loc` 的注释（cxx.h:551-562）就是这么写的。这条与流式化无关。

### 3.2 用 id 比较替掉 `cond_incl->if_tok == guard_ifndef`

**事实**：`guard_ifndef`（静态，按文件保存在 `FileStack` 176/199）在 `#endif` 处与
`cond_incl->if_tok` 比较（2045），再加 `tok->kind == TK_EOF`（2048）判定"守护宏覆盖到文件尾"。
`if_tok` 另有两处用途：`#endif without #if`（2038）与 `unterminated conditional directive`（2073）
的报错位置。

**判定：成立，但形式要换。** "检查当前栈深度为 1"不是精确条件（同一文件可以有多个
`#ifndef`，也可以嵌套）—— 精确形式是**条件帧序号**：

* `push_cond_incl()` 给每个帧发一个单调 `seq`；
* `detect_include_guard1()` 记下该文件的 `guard_seq`（而不是 `Token *guard_ifndef`）；
* `#endif` 时比 `cond_incl->seq == guard_seq` 即可，与栈深度无关；
* 报错位置改成 `Loc cond_if_loc`（`Loc` 本就设计成能比池子活得久）。

**同一类问题里更硬的一处**：`guard[].macro`（1666）**跨整个编译持有 `Token *`**，并用它做
`find_macro(guard[i].macro)`（1885）判断"这个被守护的头文件已经读过了"。流式化＋回收之后
这个指针必失效 —— 改成存**宏名 `id`**（`intern` 后的 `uint32_t`）+ 按 id 查宏表即可。

### 3.3 `join_adjacent_string_literals`

**事实**：两个 pass（2627-2661 先统一编码前缀并逐记号 `convert_str_literal` 解码，
2664+ 再拼接），同时承担 `convert_str_literal`。`-E` 的打印发生在它**之前**
（main.c:1032 打印，1039 才 join）。

**判定：成立，三点补充。**

1. **必须在输出层做**（宏展开之后）：`"a" EMPTY "b"` 只有展开后才相邻 —— phase 6 在
   phase 4 之后；lexer 看不到这种相邻性。
2. **顺序是语义的一部分**：`-E` 打印的是**未合并**的记号（gcc/clang 同样如此），所以
   "合并"只能是 parser 侧消费者看到的行为，`-E` 消费者不合并。流式实现里这等于两个钩子。
3. **指令里的 `#include "a" "b"` 不能因为"直接跳到行尾"就丢掉诊断**：今天由
   `skip_line()` 发 extra-token 警告（preprocess.c:215 `WG_EXTRA_TOKENS`）。流式跳过时
   要保留"本行还有非空白记号"这个检查，否则少一条诊断（tcctests 里有依赖它的用例）。

### 3.4 `filter_tokens` 不再需要

**判定：成立，而且比你说的更强。** 实测：正常运行里它**一个记号都不丢**
（`TK_WS`/`TK_NL`/`TK_COMMENT` 只在 `-dump-raw-tokens`（`opt_keep_ws_comments`）下生成，
lexer.c:1004/1017/1043；计数得 `ws = 0`）—— 它今天就是**一条纯遍历**，只为那个调试模式留着。
main.c:928 那份 `filter_tokens` 丢的是 `TK_LINE`（行标记），只为 `-E` 打印服务。

流式化后：两份 `filter_tokens` 都消失；`-dump-raw-tokens`/`-dump-tokens` 保留一条
"物化"路径（调试模式，不在热路径上）。

### 3.5 宏展开引擎维护一个 token 流

**判定：成立，且现状已经有一半。** 需要明确的是**四类源**与**一条回退能力**：

| 源 | 现状位置 | 流式后 |
|---|---|---|
| 文件 | `tokenize_file()` + `*rest = tok2`（1882-1898） | 文件源按需产出 |
| 宏体/实参展开 | `copy_body()`(887)、`subst()`(1014)、`expand_macro()`(1218) | **保持物化小表**，产物压进输出栈 |
| `#embed` 生成 | `emit_embed()`(1589) 往流里塞逗号分隔的字节值 | 第四类源（生成器） |
| 命令行 `-D/-U` | `prep_cmdline()` | 文件源的特例 |

**不能简化掉的一条**：`rescan_call()`（1163-1201）会**撤回已经产出的记号**
（`before->next = NULL`）并**窥视输入流后面的记号**（1172 `in->kind != TK_LPAREN`）。
所以流式化只做在**外层**（文件/段），宏展开引擎继续按"每次展开物化成小表"工作 ——
把 `expand_macro`/`subst` 逐记号流式化会直接丢掉 C/0048/0048_0087 与 C/0054/0054_0102
那两类语义（hideset 的 `noexpand` 戳、`origin` 链）。

### 3.6 让 lexer 在字符串扫描里跨空白继续

**判定：不安全，建议不做。** 三条理由：

1. 指令行里**不能**合并：`#include "a" "b"` 必须保持两个记号才有 extra-token 诊断；
2. 宏分隔的相邻串 lexer 看不到（见 3.3-1）；
3. 合并还要做**前缀统一**与 `unsupported non-standard concatenation` 诊断
   （preprocess.c:2652），这属于 phase 6 —— 放输出层只有一处实现，放 lexer 就变成两处。

唯一收益是"少产生几个记号"，与 3.4 同源，不值得为它复制一份语义。

### 3.7 实时行号与增量行偏移表

**判定：成立。** 今天 `get_location()`（lexer.c:1420+）在 `SrcFile.line_offsets`
（cxx.h:346）上二分，表由 `tokenize()` 一次性建好（lexer.c:1412）。

**补充**：行首表必须**整份保留**（与字节是否常驻无关）：`Loc` 只有 `(file_uid, loc)`，
`get_location()`（lexer.c:1420+）靠这张表把它换成行列，而诊断可以在 parse 期任意时刻对一个
很旧的 `Loc` 发问。成本可以忽略：每行 4 B，sqlite3.c 31 万行 = 1.2 MB。增量 append 即可，
`get_location()` 的二分不用改。

## 4. 输出层管线（顺序就是语义）

今天的顺序（preprocess.c:2706-2719 + main.c:1032-1039）：

```
filter_tokens → preprocess2（展开 + 段内 _Pragma） → scan_pragma_op
  → convert_keywords → convert_ppnumber（含 convert_char_literal）
  → [-E 在这里打印]
  → join_adjacent_string_literals（含 convert_str_literal）
  → parse
```

流式化后，`next_tok()` 内部固定为：

```
从展开栈取一个记号
  → _Pragma 处理（scan_pragma_op 的语义）
  → keyword 化（convert_keywords）
  → pp-number / char 转换（convert_ppnumber / convert_char_literal）
  → 字符串合并 + 解码（join_adjacent_string_literals + convert_str_literal）
  → 返回给 parser
```

两个必须保留的钩子：`-E`/`-M` 消费者要在**合并之前**取记号；`-dump-raw-tokens`
要在**全部转换之前**取记号（保留物化路径即可）。

## 5. parser 侧接口（细化）

**事实**（实测/统计）：parser **没有全局游标**（`^Token *tok;` 0 个），游标是函数参数
（95 个 `Token **rest`、117 处 `skip(tok,…)`、357 处 `Token *`）；最深前瞻只有 **2 个记号**
（`tok->next->next` 全文件 14 处）；`find_typedef()`（1015-1021）**只看 1 个记号**；
`is_typename()` 是**不消费**的谓词（14 处调用）；`skip_leading_attrs()`（8 处）要不消费地
走过属性；只有 2 处 `tok = start;` 式回退。

**设计**：

* **保留 `tok`/`rest` 形态**，不改 95 个签名（改成 tcc 的全局游标要动 456 处 `->next`，
  收益为零）；
* 在 pp 与 parser 之间放一个**可增长、可回退的记号缓冲**：
  `peek(n)`（不足则拉）、`save()/restore()`（缓冲内下标，**不是** pp 状态快照）；
* 因此 **不需要** `TentativeParsingAction` 式的全状态保存/恢复 —— 只要缓冲不丢，
  试解析（丢弃 `rest`）与 `is_typename`/`skip_leading_attrs` 的前瞻都自然成立；
* **回收**：游标之前的记号可回收，但前提是 §3.1 里那 10 处长期 `Token *` 先变成 `Loc`
  （cxx.h:685/771/1117/1179/1401/1523/1580/1596 + `guard[].macro` + `cond_incl->if_tok`）。

## 5b. 阶段 4：记号表示（打包字）——结论与不变量

这一节把前几轮的结论定死：**记号流不再是"记号结构体链表"，而是一个 `u32` 数组**，
宏体是一段自带终止符的独立数组，展开 = 把宏体复制进流缓冲区并移动游标。
依据：`doc/perf.md` §8cq（微基准：同一份 1.28 M 记号的真实流，64 B 链表 **6.84 ns/记号、
81.8 MB**，打包数组 **2.39 ns/记号、6.2 MB** —— 遍历快 **2.9×**、内存少 **13.2×**；
tccgen 的整份记号只有 3 MB、**装得进 L3**，链表仍慢 2.7× ⇒ 代价主要来自**指针追逐的依赖链**，
不只是容量）与 §8cr（驻留表：`id = h | (slot << 12)`，`max_id ≤ 76,421`、`max_slot ≤ 18`）。

### 5b.1 打包字的形状

```
0                                    终止符 / EOF
kind (< 4096)                        普通记号（标点、运算符、结构关键字）
id   (>= 4096, 最高位 0, 高 4 位标志)  标识符（拼写在 intern 表里）
BIT31 | (kind << 20) | (值 ≤ 32 位)    TK_CHARLIT（值内联）、TK_LINE
BIT31 | (id << 12) | STR_TAG          TK_STR（值 = intern 的已解码值，仍是一个字）
BIT31 | (pool_index << 12) | NUM_TAG  TK_NUM —— **唯一走 16 B 值池的**
```

* **值池只服务 `TK_NUM`**（`ival` = `Int128`、`fpval` = `Fp128`，各 16 B）。字符串的值本来
  就是 intern id（lexer.c:449/472）、字符常量的值 ≤ 32 位 ⇒ 都不需要池。实测值记号只占
  **5.2%（sqlite3，pp_number 67,018）/ 2.4%（tccgen）** ⇒ 均摊 ≈0.8 B/记号，与 §8cq 的
  4.8 B/记号吻合。
* **id 改成"稠密序号"而不是"哈希打包值"**（比"槽位 0 不用 ⇒ id ≥ 4096"更干净，后者只是
  在旧编码上打补丁）：`intern` 除了哈希去重，再往一张动态增长的数组里追加
  `{char *str, uint32_t len}`，**id 就是这条记录的下标**。于是分段约定是：

  ```
  [0, TK_NKIND)        结构性 kind（标点、运算符；枚举常量）
  [TK_NKIND, KW_END)   关键字段：注册顺序固定 ⇒ 每个关键字既是枚举常量又是它的 id
  [KW_END, ...)        普通标识符（稠密序号）
  ```

  `TK_INT` 因此**仍然是编译期常量**：现有 `kw[]`（lexer.c，**76 个关键字**，顺序固定）就是
  那张登记表，启动时按表顺序注册，枚举项 = 段基址 + 表内下标，或者在启动时
  `assert(intern(kw[i].keyword) == 枚举值)`。判别代价都变成一次比较：
  `kind < TK_NKIND`（结构）、`TK_NKIND <= kind < KW_END`（关键字）、`kind == TK_IDENT`
  且载荷是 id（普通标识符 —— 也可以让普通标识符的 kind 直接等于 id，`TK_IDENT` 全树只有
  **55 处**，但保留 `kind == TK_IDENT` + 载荷放 id 可以一处都不改）。`convert_keywords()`
  那一趟随之消失（§8cp 实测 0.25%/0.31% 的 cc1）。
  好处是 `str(id)`/`str_len(id)` 变成一次数组索引，`is_keyword(id)` 一次比较（哈希打包的
  id 既不连续也不小，做不到这两件事）。**注意 id 不再是 0**（第一项从 `TK_NKIND` 起），
  与"`0` 只做终止符"自洽。
* **前后缀编进 kind，值种类自成一个连续段**（由"kind 编码"讨论定稿）：
  `TK_NUM_UL`、`TK_NUM_LL`、`TK_STR_U8`、`TK_CHAR_L` 这样把 `lit_suffix`/`enc_prefix`
  **直接编码成种类**，于是
  ① `Token` 少两个字段（今天 `lit_suffix` 是 12 位标志、`enc_prefix` 是 5 值枚举）；
  ② 判定变成种类比较（值类型只有 4 个基本形 + 其后缀变体）；
  ③ **值种类连续** ⇒ `word >> 12` 就是值池下标，**不需要额外的标记位**（这正是 §8cr 里
  那个"带值记号需要标记位"的干净解法）：

  ```
  0                                  终止符 / EOF
  [1, TK_NKIND)                      普通结构 kind（标点、运算符、结构关键字）
  [TK_NKIND, VALUE_END)              带值 kind（数字/串/字符/行标记的各个前后缀变体）
                                     字 = (池下标 << 12) | kind
  [KW_FIRST, KW_END)                 关键字（枚举常量 = 注册顺序，见下）
  [ID_FIRST, ...)                    普通标识符的稠密序号
  ```

  实测规模（`cxx.h` 的 `SUF_*` 是 12 位标志，但**有效组合远少于位宽**）：整数 6 种
  （无/u/l/ll/ul/ull）、浮点 5 种（f/l + C23 的 f16/f32/f64/f128）、bitint 1 种、
  串与字符各 5 种前缀（无/u8/u/U/L）⇒ **约 23 个新种类**，`TK_NKIND` 从 131 到 ~154，
  离 4096 很远。改动面是**把 117 处标志测试换成种类比较**（`lexer.c` 58、`literal.c` 32、
  `preprocess.c` 18、`parser.c` 9）。
  **例外一个**：`SUF_NONDEC`（0x800）不进 kind —— 它不是类型后缀，而是 pp-number 的**值**属性
  （非十进制），`#if` 求值要用（`preprocess.c:593` 那里还专门把它保下来），所以它留在值侧。
* **实现时要逐处核对的**：全树有 **15 处拿 id 的低位当哈希**（`parser.c` 作用域/标签表 7 处、
  `preprocess.c` 宏表 4 处、`dumpir.c` 2 处、`lexer.c` 2 处），其中 lexer.c 的注释明写
  "id 的低位携带 intern 表自己的哈希，用它索引这张表"。改成稠密序号后 `id & (cap-1)` 变成
  "连续整数取模"——对开放寻址未必更差（对 2 的幂是一个置换，甚至更少冲突），但要**逐处实测
  填充率**，不能假设；`intern` 本身也多了稠密表（实测 `max_id ≤ 76,421` ⇒ 约 1.2 MB）与一次
  间接（§8cj 量过 `intern` = 4.28% 的 cc1、~125 Ir/次），需要重测。内置函数（`add_builtin`，
  12 处）是**宏**而不是 token kind，不占这段 id 空间。
* **`enc_prefix` / `lit_suffix` 不进 kind**：编码前缀（5 种 × 串/字符）与数字后缀（12 位标志）
  放进打包字的富余位，种类保持在一百上下（今天 `TK_NKIND = 131`，远小于 4096）。

### 5b.2 不变量（六条，实现时逐条对照）

1. **hideset 用栈，`noexpand` 用 1 个 bit**。抑制栈（以 0 结尾的 id 数组）表达 `is_disabled`
   这种**动态作用域**：扫宏替换表期间它的名字不可替换，入栈/出栈随递归自然调整。但
   6.10.4.1p2 的那个戳是**逐记号持久**的（"that lasts beyond the scan"，C/0048/0048_0087），
   栈表达不了 ⇒ 输出流里那个字上留 1 bit。
2. **空白位逐记号记**。`is_sol`/`is_leadingws` 对"流里当前的"记号可以是流式状态，但
   **stringize（`#x`）要还原实参自己内部的空白**（`join_tokens` 读的正是实参每个记号的这两位），
   那是扫描时的属性 ⇒ 扫到时就写进那个字（富余位）。
3. **拼写三分工**：标识符 → intern 表（字里放 id）；字符串 → 同一张表（值即 id）；
   数字 → 值池；**宏实参的拼写（含原始空白）在收集时记 `(offset, len)`**（`#`/`##` 用它，
   它不能从 kind/id 还原）。诊断的源码行与 `^~~~` 仍要文件字节常驻。
4. **展开要有一个显式的"展开帧栈"**：缓冲区有**读游标 + 写游标**，展开 = 把宏体追加到写端、
   读游标跳到追加处重扫；一个宏体扫完弹帧。C/0048、C/0054 那些语义就落在这个栈上
   （今天它是 `expand_macro(dst, sub)` 的递归链表版）。
5. **投机解析期间缓冲区只追加、不回收**；`Commit()` = 丢弃缓存并移动预处理器数组指针，
   `Revert()` = 回退指针。要列清"移动游标撤不回来"的副作用：`__COUNTER__`（cxx 有此内建）、
   `intern` 表增长、`input_files` 注册；条件编译状态是安全的（指令在 parser 之前处理完）。
   **parser 侧的试解析必须保持无副作用**（今天成立：`is_typename` 不消费、试解析靠丢弃 `rest`），
   这条作为不变量写下来。
6. **`0` 只能是终止符**：宏体的终止符不要复制进流（否则流被提前截断）；反之 `0` 必须
   不可能是真记号（`TK_EOF == 0`，且 id ≥ 256 见 5b.1）。

### 5b.3 关键字 = intern id：可选，收益 ≤0.3%

启动时 `intern("int",3)` 之类注册关键字/内置函数名，于是"它的 id 就是它的类型"，
`convert_keywords()` 那一趟消失。核对结果：lexer **已经在给每个标识符取 id**（lexer.c:1202）；
令牌种类上的 `switch` 几乎没有（grep 到的 `switch(kind)` 基本是 AST/type 的 kind）；
只有 **3 张按 kind 索引的表**要加"是关键字"的判定（`lexer.c:53 expect[TK_NKIND]`、
`parser.c:4841 op_table[TK_NKIND][2]`、`parser.c:5554 as_op[TK_NKIND]`）。

但 **`convert_keywords` 整遍实测只有 0.25%（sqlite3）/ 0.31%（tccgen）的 cc1**（§8cp），
其中大头是"每个标识符一次哈希探测"，那部分**不会消失**（生产时判定同样要查一次）⇒ 省掉的
只是那趟遍历 ≈ **0.1~0.15% 的 cc1**（折 `cxx -c` 约 0.05%）。代价是三条：

* 枚举常量变运行期变量 ⇒ `switch` 的 `case TK_INT` 不合法、`-Wswitch` 的穷尽性检查对关键字
  失效（这个安全网前几轮真抓过 bug）⇒ 折中：**结构性 kind 保留枚举，只让"大量同义词"
  （类型关键字、内置函数名）走 id**，或更保守地**保留枚举、只把转换挪到生产时**（收益相同、零风险）；
* **上下文相关的名字不能提前定型**：`defined`（只在 `#if` 里）、`_Pragma`（在输出流里当运算符，
  且要等宏展开之后）、`__has_include`/`__has_attribute`、`__VA_ARGS__`/`__VA_OPT__`；
* 关键字 id 不连续也不小（`id = h | (slot<<12)`）⇒ 想要便宜的 `is_keyword(id)` 得显式留位
  （复用 5b.1 的"桶避开低位带"）。

**结论：做成"可选优化"写进编码约定，不作为迁移的驱动力。** 5b.1 与 5b.2 才是必须先定死的。

### 5b.4 它让哪些难题消失

| 原来难的地方 | 打包字之后 |
|---|---|
| `copy_body` 每次展开复制宏体（今天每记号 64 B 分配，sqlite3 有 467k 次复制） | 一次 `memcpy` 若干 u32（总量 ≈2 MB） |
| 宏体借用"定义它的文件"的字节 ⇒ 文件必须常驻 | 宏体自带数组 ⇒ 该文件的流记号消费完可**整段回收** |
| `rescan_call` 要把已产出的记号"取回来"（`before->next = NULL`） | 缓冲区游标回退一格 |
| `push_disabled` 每次展开 `emalloc` 一个 `Hideset` 节点 | 一个 int 抑制栈 |
| 阶段 3 的回收要"按 chunk 猜存活" | 按段/按文件流整段回收 |

**代价**：`->next` **867** 处、`->kind` **1123** 处、`Token *` **727** 处、`Token **`（rest 出参）
**137** 处（parser.c 占 413/528）——这是"重写前端数据表示"级别，必须在阶段 2/3 的同一次迁移里做。

## 5c. 标识符池与同名链（结论）

与 §5b 配对：§5b 定"记号字长什么样"，本节定"id 从哪来、宏与符号挂在哪"。

### 5c.1 两个池子彻底分开

今天 `intern` 一张表服务所有字符串（标识符、字符串字面量的已解码值、文件名、宏粘贴结果、
指令名……），id 同时是"哈希打包值"（`h | (slot << 12)`），并被 **15 处**拿低位当哈希索引
（`parser.c` 7、`preprocess.c` 4、`dumpir.c` 2、`lexer.c` 2 —— 其中 lexer.c 的注释明写
"id 的低位携带 intern 表自己的哈希，用它索引这张表"）。改成两个池子：

* **标识符池**：每条记录是一个拼写的"身份证"，除 `{char *str, uint32_t len}` 外还挂
  `Macro *macro`、同名链（5c.3）、名空间链与内置语义信息；**`id` = 记录下标**（稠密序号）。
* **串池**：字符串字面量的已解码值、文件名（`display_name`/`file_identity`）、`paste()` 的合成文本、
  预处理器指令名与 `dt[]`、`strlit` 表。只存 `{char*, len}`。

好处：① `str(id)`/`str_len(id)` 一次数组索引；② 只有标识符需要那些额外字段，串池不必为它付费；
③ `TK_STR` 的载荷变成"串池下标"，与 §5b.1 的标记位约定一致。分池要**逐个审计 `intern` 的调用点**
（几十处），归错类会出现"拿串池 id 当 ident 用"的隐性错误。

### 5c.2 宏查找变成一步，但阶段不能编进 id

`ident->macro` 让宏查找从 `macro_ht[id & (macro_cap-1)]` + 链遍历变成**一次装载**
（`preprocess.c` 那 4 处低位哈希随之消失），`#define`/`#undef` 就是置/清这个字段。

**但不要按"预处理期 ident / 编译期 ident"切 id 空间**：同一个拼写在不同时刻扮演不同角色 ——

```c
#define A 1
int x = A;      /* A 是宏 */
#undef A
int A = 5;      /* A 是普通标识符 */
```

所以是**一个池子**，每条记录同时能挂 `macro` 和符号链；"当前是什么"是**运行期状态**
（`macro` 是否为 NULL），不是 id 的属性。分段约定（id 就是记录下标）：

```
[0, TK_NKIND)        结构性 kind（标点、运算符；枚举常量）
[TK_NKIND, KW_END)   关键字：注册顺序固定（lexer.c 的 kw[]，76 个）
                     ⇒ 每个关键字既是枚举常量又是它的 id，TK_INT 仍是编译期常量
[KW_END, ...)        普通标识符（稠密序号）
```

`TK_INT` 保持常量的做法：启动时按 `kw[]` 的顺序注册，枚举项 = 段基址 + 表内下标，或者启动时
`assert(intern_ident(kw[i].keyword) == 枚举值)`。判别都变成一次比较（`< TK_NKIND` 结构 /
`[TK_NKIND, KW_END)` 关键字 / 其余标识符），`convert_keywords()` 那一趟消失（§8cp 实测
0.25%/0.31% 的 cc1）。内置函数（`add_builtin`，12 处）是**宏**而不是 token kind，不占这段空间。

### 5c.3 同名链：深度降序 + dead 位 + 遍历重连

每个 ident 挂一条"同名声明链"（普通名空间与标签名空间各一条，对应今天的 `ht`/`tht`），
替代 parser 每个作用域一张 `ht[id & (cap-1)]`（7 处）。查找变成沿一条链走，**无哈希**。

**惰性移除可行**：退出作用域时不必逐链摘除。顺带澄清一点成本：急切摘除也不是
O(程序里的标识符数)，而是 **O(该作用域的声明数)** —— `leave_scope()` 本来就要走一遍该作用域的
符号，所以两条路同级；惰性的好处是**退出作用域零链操作**（深嵌套、声明密集的代码受益）。
要用惰性，需要三样东西才正确：

**① dead 位（+ 所属作用域）**。只比深度会错，同深度的兄弟作用域：

```c
{ int i; }        /* 结点 A：深度 3 */
{ int i = 5; }    /* 结点 B：深度 3；在这里查找 i，只看深度会把 A 当成活的 */
```

深度只在两个单义情形里能一击判定：`node->depth < cur_depth` ⇒ **必定活**（已退出作用域的结点
深度只会 ≥ 当前深度）；`node->depth > cur_depth` ⇒ 必定死；`==` 有歧义，交给 dead 位。

**② 链按深度降序插入**。注册顺序与嵌套深度不单调，"遇到第一个活的就停"会取错：

```c
void f(void) { { int x; } }   /* 结点 B：深度 3，先注册 */
int x;                        /* 结点 A：深度 1，后注册 ⇒ 在链头 */
void g(void) { { int x = 7; } }  /* 链 = [A(活,深度1), B(dead,深度3)]，正确答案是 B */
```

按深度降序插入后，当前深度的结点总聚集在前段、插入点靠近头部，早停才成立：
"跳过 dead，遇到第一个 `depth <= cur_depth` 且活着的结点就是答案"。

**③ 诊断要跳 dead，遍历要重连**。`previous definition is here` 若指到已退出作用域的符号就错了
（这正是 dead 位不能省的原因）；遍历时顺手把前驱的 next 直指后继 ⇒ 链**自我修复**，
dead 结点第二次遇到时已不在链上，"变长"只是暂时的。

另外两点：C 有多个名空间（普通名、标签名、成员名、标号），ident 要挂多条链；作用域深度不止三级
（`for`、复合语句、原型作用域各自成层），用 `uint16_t` 的任意非负整数。

### 5c.4 收益与代价

| | 收益 |
|---|---|
| 宏查找 | `ident->macro` 一次装载（`find_macro` 每个标识符记号一次）|
| 符号查找 | 一条同名链、无哈希，深度降序 ⇒ 常见 1~2 步 |
| 删掉的东西 | **15 处** `id & (cap-1)` 低位哈希 + 5 张哈希表（宏表 1 张 + 每作用域 1 张）|
| `convert_keywords` | 整趟消失（0.25%/0.31% 的 cc1，§8cp）|
| `str(id)` | 一次数组索引 |

代价：ident 记录多 `Macro*`(8) + 同名链 `next`(8) + dead/深度/作用域(4~8) ≈ **+24 B/拼写**，
实测规模 `max_id ≤ 76,421`（§8cr）⇒ 约 **+2 MB**；`intern` 多一张稠密表（同量级）与一次间接
（`intern` = 4.28% 的 cc1、~125 Ir/次，§8cj），要重测。收益总量级（宏查找 + 符号查找 + 删表）
必须在原型上量，不能拍。

### 5c.5 实现顺序（每步都能单独过全套闸门）

1. **ident 池 + `ident->macro`**（不动 token 表示）：宏表哈希消失、`find_macro` 变一次装载；
2. **`prev` 同名链**替换 parser 的 per-scope 哈希表（深度降序 + dead 位 + 遍历重连）；
3. **打包字**（§5b）：此时 id 已是稠密 ident 下标，水到渠成。

三步都以 `doc/tcctests.sh` 106 / conformance 326 / c2y 101 / IR 与 `-E` 逐字节为网。

## 8. 位置信息的来源：**预处理器上下文**，而不是记号（本轮定的方向）

### 8.1 终点与过渡

| | 形态 | 说明 |
|---|---|---|
| **终点** | `uint32` 数组 ✓ | 记号位置在节点里只留一个 **32 位下标** ✓ —— 一个数组、一次索引 ✓，没有中间结构、没有多余解引用 ✓ |
| **过渡** | `Node->tok` → `Node->loc` ✓ | 先把"节点里的记号指针"换成"节点里的位置" ✓，语义立刻正确 ✓，成本立刻下降 ✓ |
| **不要** | `SrcLoc{uid,loc}` + `tok_at()` 这类中间物 ✗ | 半中间的改造**依旧是结构体** ✓ ⇒ 平白多一层解引用 ⇒ **净亏损** ✗（我先前那一版正犯此错 ✓） |

### 8.2 为什么不必从记号取位置

流式解析前端**本来就知道当前位置** ✓ ——
预处理器上下文里保存的正是"**从哪里继续**"的那个位置 ✓，
它既是流式产出下一个记号的依据 ✓，也就是"**当前正在消费的记号的位置**" ✓。

⇒ 于是在**创建 AST 节点时直接向上下文要位置** ✓，而不是"拿到记号 ⇒ 再读记号的字段" ✗。
这条一旦成立 ✓，`tok` 就**只剩"位置诊断信息"一个用途** ✓ ——
这正是它最终能退化成 `uint32` 的原因 ✓。

### 8.3 随之而来的必要改动：**创建点前移 + 回填**

脱离"从记号取位置"之后 ✓，节点的创建时刻必须提前到**消费该记号的那一刻** ✓：

```
以二元 + 为例：
  见到 '+' ⇒（此刻上下文的位置就是 '+' 的位置 ✓）⇒ 立刻创建 ND_ADD 节点、填好 loc ✓
  ⇒ 解析右操作数 ⇒ 回填到 rhs ✓
```

⇒ 而不是先解析完右操作数、再拿某个记号去创建节点 ✗。
这是一次**结构性的前移** ✓，涉及所有"运算符/关键字先出现、操作数后解析"的节点 ✓
（二元 ✓ 一元前缀 ✓ 强制转换 ✓ 复合字面量 ✓ sizeof ✓ 声明符 ✓ …），
而它恰好**就是"parser 驱动、按需产出"的一部分** ✓：
**解析器在消费点决定要什么 ⇒ 预处理器才产出** ✓✓。

### 8.4 对已完成工作的影响

* **保留** ✓：§8dw 的 `LineMark` 表（`filename`/`line_delta` 由 `(file_uid, loc)` 推出 ✓）、
  §8dl 的流式 `-E` ✓、§8dh 的 `pp_out`/`pp_emit` ✓、§8dp 的 `pp_yield`/`pp_resume` ✓ ——
  这些是"流式"本身 ✓，与新方向一致 ✓；
* **作废** ✗：为"从记号链取位置"而写的 `tok_at()` / `SrcLoc` / `loc_from()` 一族 ✓
  （以及为它们服务的补丁器事故排查 ✓）—— 它们解决的是一个**本不该存在**的问题 ✓；
* **已落地的工作树**（十处 ✓、全绿 ✓、conformance 326/0 ✓）不受影响 ✓，
  因为那条路走的是 `Loc` 与流式产出 ✓，没有引入 `SrcLoc` ✓。

## 9. 终点的记号形态：**两个全局变量 + `next()`**（本轮定的方向）

### 9.1 目标

| 项 | 形态 |
|---|---|
| `tok` | `uint32` —— **当前记号的 kind** ✓ |
| `tokc` | **当前记号的值** ✓ |
| 谁填充 | **预处理器** ✓ |
| 解析器怎么要下一个 | `next()` ✓ —— 让预处理器**产出**一个记号并填进上面两个全局 ✓ |
| 前瞻怎么办 | **以状态表达** ✓ —— 指示"当前 tok 暂时不消费" ✓（即 peek 不推进 ✓）|
| 记号数组 | **最终不存在** ✗ —— 所谓的"token 数组"只在**预处理器内部** ✓，用于**前瞻与宏展开的缓存** ✓ |

⇒ 记号的**按需产出、按需消费、消费即消亡** ✓ ——
这正是"parser 驱动、token 按需产出"的**字面含义** ✓，也是本目标的终点 ✓。

### 9.2 为什么这样能省掉一整类负担

* 解析器**不再持有**记号的指针或名字 ✓ ⇒ 不存在"记号被回收而指针悬空" ✗ 的问题 ✓；
* 宏展开需要的前瞻/回退 ✓ **关在预处理器内部** ✓（它有自己的缓存 ✓），
  解析器只看见"当前这一个" ✓ ⇒ 前后端职责切开 ✓；
* §8ep 的**分块回收**因此变得自然 ✓：解析过的记号**立刻可回收** ✓ ——
  只要解析器不再指向它们 ✓（这正是本节要求的那条 ✓）。

### 9.3 对位置信息的影响（**修正第 2b 步的一个本质假设** ✗）

我原先把 `Node->loc` 设计成"**记号在 arena 里的名字**" ✗ ——
那**仍然依赖记号存在** ✗，而终点形态里记号**消费即消亡** ✗✗ ⇒ 名字会失效 ✓。

⇒ 正确的含义是：**节点里存的是"位置"** ✓ ——
由**消费点**从上下文取 ✓（§8 的 `pp_cur_loc()` ✓ 就是那个来源 ✓），
以**位置表的名字**（4 字节 ✓）或**一个 Loc 值**表示 ✓，
与记号的生命周期**无关** ✓。

**代价的账（用户明确给出 ✓）**："原来的 `ast->tok` 取位置信息 ✓，现在用 `loc` ✓，
**都是一次解引用** ✓，代价并没有变高 ✓" ⇒
**不必**为了省一次解引用而绕道结构体或多余指针 ✗ ——
真正要减的是**对 token 的依赖** ✓，不是解引用的次数 ✓。

### 9.4 与已完成工作的衔接

* §9 之前做的 ✓：`pp_cur_loc()` ✓（位置来源 ✓，已落地证明惰性 ✓）、
  流式 `-E` ✓、`LineMark` 表 ✓、`Token` 瘦到 48 B ✓ —— **全部仍然有效** ✓；
* 第 2b 步（`Node->tok` → `uint32 loc` ✓）**方向正确** ✓（去掉指针依赖 ✓），
  但 `loc` 的**含义要按 §9.3 定为"位置"** ✓ —— 现阶段它暂存"记号名字" ✓
  只是为了先让整棵树编译通过 ✓（scratch 树里已从 62 处降到 8 处 ✓），
  **换含义是一步小改动** ✓（`loc_of_tok()` → `loc_of_here()` ✓），而**不是重做** ✓。

## 10. 构造函数**不再传位置**：只有 `new_node` 自己从上下文取（本轮定的方向）

### 10.1 规则

| 函数 | 参数 | 位置从哪来 |
|---|---|---|
| **`new_node(kind, …)`** | **不带位置** ✓ | **函数体内**直接从**当前上下文**取 ✓（`pp_cur_loc()` ✓）并写入节点 ✓ |
| **其余构造函数**（`new_unary`/`new_binary`/`new_num`/`new_var_node`/… ✓）| **不带位置** ✓ | **不需要** ✗ —— 它们**最终都调用 `new_node`** ✓，位置在那里取 ✓ |

⇒ 一句话 ✓：**位置的采集点只有一个** ✓ —— `new_node` 的函数体 ✓。
⇒ 于是**调用点不必提供位置** ✓ ⇒ §8ic 那一族"调用点与签名不匹配"（259 个错误 ✓）
**整族消失** ✓✓ —— 不是被修好 ✗，而是**不再存在** ✓。

### 10.2 代价：很多构造要**先造节点、再回填操作数**

`new_node` 在**被调用的那一刻**取位置 ✓ ⇒ 若某个构造是"**先算完操作数、再建节点**" ✗，
它取到的位置就**晚于**该位置应有的地方 ✗（例如 `+` 会指到右操作数之后 ✗）。
⇒ 这些地方必须改成 ✓：**先建节点**（此刻取位置 ✓）⇒ **再解析操作数** ⇒ **回填** ✓。

这正是 §9.3 说的"**创建点前移 + 回填**" ✓ ——
而本节把它的**范围缩小**了 ✓：只需改**位置会取错**的那些构造 ✓，
而不是改所有构造的签名 ✓。

### 10.3 对已完成工作的处置

* **保留** ✓：`Node->loc` 字段 ✓、位置表（`loc_name`/`loc_get`/`loc_str` ✓，§8gz ✓）、
  `pp_cur_loc()` ✓（§8gr ✓ 已落地并证明惰性 ✓）、四条规则里的**不涉签名**的部分 ✓
  （`diag` ✓ `spelling` ✓ `write_*` ✓ `loc_test` ✓ `loc_field` ✓ `loc_ternary` ✓ `text_of` ✓）；
* **作废** ✗：`_r615_helpers_loc` / `_r625`→`_r660` 那一串"**把函数签名逐个换成收位置**"的补丁 ✓
  —— 它们解决的问题**不该存在** ✗（构造函数本来就不需要那个参数 ✓）。
  同理，`rule_call_site` / `rule_call_token` 这两条"调用点跟随签名"的规则 ✓ 也不再需要 ✓；
* **教训（记 ✓）**：我在 §8gl–§8ic 花了十余轮，把"**给每个函数换参数**"这件事做得越来越对 ✗ ——
  而正确的动作是**把参数的来源收敛到一个函数里** ✓。
  ⇒ 与 §8gp 那句"**先确认来源，再谈变换**"是同一条 ✓：
  **这次要确认的是"这个参数本来需不需要存在"** ✓。

## 11. `tok`/`tokc` 接口（主线）：`next` / lookahead / commit / rollback

### 11.1 现在的做法不是目标

"**cpp 全部跑完，再把整条记号链交给 parser 解析**" ✗ —— 这只是当前实现 ✓，
**不是设计目标** ✓。目标里**parser 是驱动者** ✓：

| 动作 | 谁发出 | 效果 |
|---|---|---|
| `next` | **parser** ✓ | 指示 cpp **产出一个记号**；cpp 回填 **`tok`**（kind ✓）与 **`tokc`**（值 ✓），并回填**全局 `loc`** ✓（它在位置表里的位置 ✓）|
| **lookahead** | parser ✓ | 置"**不消费**"的状态 ✓ —— 当前的 `tok`/`tokc`/`loc` 保持 ✓ |
| **commit** | parser ✓ | 试解析**成功** ⇒ **什么都不动** ✓ |
| **rollback** | parser ✓ | 试解析**失败** ⇒ 把 `loc` **回退**到试解析之前的值 ✓ ⇒ **parser 换一条路再试时，位置信息仍然正确** ✓ |

⇒ 于是 `new_node` **直接读全局 `loc`** ✓ —— 全树仍然只有一处取位置 ✓（§8id ✓），
而**这一次它的来源真的是"当前"** ✓（不再是"cpp 当年的位置" ✗）。

### 11.2 位置表的分工（行号在表里 ✓，列号在节点里 ✓）

* **表项精确到行** ✓（`file_uid` + 行 + 行内起始偏移 ✓）⇒
  **同一行的多个节点复用同一个表项** ✓ ⇒ 重复大幅减少 ✓；
* **列号放在节点里** ✓ —— 表项因此可以更小、更少 ✓；
* ⇒ 这是"**位置表 + 节点少数字段**"的分工 ✓，比"每个节点一个完整 `Loc`（20 B ✗）"省得多 ✓。

### 11.3 列号的偏移：**允许存在的临时状态** ✓

当前版本的诊断**行号已经正确** ✓、**列号有偏移** ✗ —— 而**行号正确**说明
"位置信息并没有大错" ✓：偏移来自**节点创建点的位移** ✓
（`new_node` 在操作数解析**之后**才被调用 ⇒ 当前记号已经前移 ✓）。
⇒ **允许暂时保留** ✓，统一到**后续收尾阶段**修正 ✓
（那时做的是"创建点前移 + 回填" ✓ —— §9.3/§10.2 ✓）。
⇒ **不因此停下主线** ✓。

### 11.4 第一步（本轮起 ✓）

**接口先立起来** ✓，**cpp 内部暂时不动** ✗：

```
next()      —— 从现有链上取下一个记号 ⇒ 填 tok/tokc/loc（并记住"试解析起点"）
lookahead() —— 只看不消费（保持 tok/tokc/loc 不变）
commit()    —— 丢弃保存的起点
rollback()  —— 把 loc（以及 tok/tokc）退回保存的起点
new_node()  —— 直接读全局 loc
```

⇒ 这一步的**验收判据** ✓：`new_node` 读到的位置 = **parser 当前所在记号的位置** ✓ ⇒
**列号偏移应当显著减小** ✓（只剩"创建点晚于记号"的那部分 ✓），
而行号**必须正确** ✓ —— 用 conformance ✓ + 三个负载的警告比对 ✓ 检验 ✓。
⇒ 之后再让 cpp **真正按需产出** ✓（把 `next()` 换成对 cpp 的指示 ✓）——
那时 cpp 内部的"整条链"才退化为**前瞻与宏展开的缓存** ✓（§9.1 ✓）。

### 11.5 预处理器内部：`tok` 与 `loc` **两个平行缓存**（用户定 ✓）

**设计（照录 ✓）**：

> 预处理器内部设置的 loc 和 tok 保持同步 ✓。也就是**产出一个 tok 写一个 loc** ✓，
> **试前瞻缓存时同步扩充 loc 缓存数组** ✓，
> 内部的 **loc 缓存位置数组和 tok 缓存数组可以保证一一对应** ✓。
> 这样语义基本就和未拆开前的 token 自带 loc 信息一致 ✓，
> 只是**拆开到了两个位置**而已 ✓。**回退 tok 指针时同步回退 loc 指针**即可 ✓。

**⇒ 这条把"位置从哪来"彻底解决了 ✓**：

* 拆分前 ✓：`Token` 自带位置 ✓ ⇒ 谁拿到记号谁就有位置 ✓；
* 拆分后 ✓：**两个平行数组，同一下标** ✓ ⇒ **语义等价** ✓ ——
  拿到记号的**下标**就等于拿到了位置 ✓；
* 而"下标"这件事 ✓ 本会话已经落地过一件工具 ✓：**`tok_index`/`tok_of_index`** ✓
  （§8gz 期 ✓）⇒ 平行数组可以直接挂在同一个下标上 ✓✓。

**⇒ 与 §8iv 的对照（这也是它的答案 ✓）**：
§8iv 里"预处理器不知道解析器在哪" ✗ ——
那是因为我当时**只在找"一个游标"** ✗（`pp_in` ✓ `pp_out` ✓ `pp_here` ✓）。
按本节的设计 ✓，**根本不需要游标** ✓：
**解析器手上就有记号 ✓ ⇒ 用它的下标去取位置即可** ✓✓。

**⇒ 实现位置（已勘察 ✓）**：`preprocess.c:2069` 一行 ✓

### 11.6 `loc` 的生命周期：**与 `tok` 同寿，除非要 `-g` / `-dump-ast`**（用户定 ✓）

**设计（照录 ✓）**：

> 只有在**尚未落地、仍在计划中的 `-g`** 以及 **`dump-ast`** 才需要在 AST 节点上附带位置信息 ✓，
> 同时 **loc 全生命周期** ✓。如果是**普通模式** ✓，
> loc 位置完全可以是**和 tok 一样只在预处理器内部使用** ✓ ——
> 当前代码解析完毕且**没有需要报错**，则 loc 位置**再也无用** ✓，此时 **loc 和 tok 的生命周期一致** ✓。
> 把他们**拆成两个**保证了他们的**生命周期解耦** ✓。
> 同时 **loc 本身是冷路径** ✓，拆出之后 **tok 轻装上阵** ✓。

**⇒ 两个生命周期（本节的核心 ✓）**：

| | 生产 | 使用者 | 何时可以丢弃 |
|---|---|---|---|
| **`tok`** ✓ | 每次 `next` ✓ | 解析器（**热路径** ✓：每个记号都要看 ✓）| **下一个记号产出时** ✓（只需一个 ✓）|
| **`loc`** ✓ | 每次 `pp_emit` ✓（§11.5 ✓）| 诊断 ✓ 与（计划中的）`-g` / `-dump-ast` ✓ | **普通模式**：最后一个可能报错的地方之后 ✓；**`-g`/`-dump-ast`**：**对象/AST 的整个生命周期** ✓ |

⇒ 拆分前 ✓，二者**被绑在一起** ✗：只要留一个记号 ✓，就**顺带**留着一份位置 ✓；
⇒ 拆分后 ✓：**留记号不留位置** ✓ —— 于是**热路径只剩 kind 和值** ✓（"轻装上阵" ✓），
而**冷的位置按需保留** ✓。

**⇒ 对当前实现的三条直接后果（可执行 ✓）**：

1. **平行数组是对的** ✓（§11.5 ✓）—— 它让"留记号不留位置"成为可能 ✓；
2. **位置表是冷路径** ✓ ⇒ 它**按行**存（已做 ✓ §8iz ✓）、**驻留**（已做 ✓ §8gz ✓），
   而它可以**在不需要时整体丢弃** ✗（普通模式且解析结束后 ✓）——这是**后续的收尾优化** ✓；
3. **`Token` 可以瘦身** ✗ —— 它现在仍带着位置字段 ✓（`file_uid` ✓ `loc` ✓ `len` ✓ `line_delta` ✓）；
   拆分后这些**不必随每个记号常驻** ✓ ⇒ 这是"tok 轻装上阵"的**记账** ✓（后续做 ✓）。

### 11.8 折叠的时机与模式（用户定 ✓）

**设计（照录 ✓）**：

> 对于折叠 ✓，**`-dump-ast` 模式需要打印原始的 AST 树** ✓ ⇒
> 所以**不折叠** ✓ 并且在打印完毕后**退出子进程** ✓。同样 **`dump-tok`** 也应该如此 ✓。
> **折叠时机可以前移** ✓，也就是**生成可能可以折叠的位置立刻尝试折叠** ✓。
> 目前完整生成之后才折叠 ✓ 导致后期需要**从 root 遍历** ✗ 走过了大量无关节点 ✗。
> 现在应该改为**解析 `2+3`**：
> **生成 lhs** ✓ → **创建 `+` 的带位置节点** ✓ → **生成 rhs** ✓ → **回填** ✓ →
> **立刻折叠 `+` 节点** ✓；可折叠的话 ✓，**`fold` 内部直接原地修改类型和值** ✓，
> **无需额外分配空间** ✓。

**⇒ 这条设计的两层收益（记下来 ✓）**：

1. **正确性/成本** ✓：折叠**不再需要**"完整生成 + 从 root 遍历" ✗ ⇒
   无关节点不再被走过 ✓，而且**折叠发生在信息最新的时候** ✓（就地可见 ✓）；
2. **位置** ✓（对当前主线尤其关键 ✓）：折叠**发生在解析器正处在该运算符**的时刻 ✓
   ⇒ `p_loc` **正是那里** ✓ ⇒ 折叠过程中发出的诊断（如"隐式转换改变了值" ✓）
   **拿到的是正确位置** ✓✓ —— 而这正是本会话卡了很久的 tccgen 那一处 ✓
   （它现在报在"**冻结的 `p_loc`**"上 ✗，因为折叠发生在**解析结束之后** ✗）。

**⇒ 另外** ✓：`-dump-ast` **本来**在 `fold_ast` 之前打印 ✓（`main.c:1094/1096` ✓，
注释原文 "dump_ast above runs before fold_ast on purpose" ✓）⇒
用户要的是**再进一步** ✓：**该模式下根本不折叠 ✓、打印完就退出** ✓。

### 11.9 永存位置表：**按下标 ✓，不按顺序找** ✓（用户定 ✓）

**设计（照录 ✓）**：

> 对于**永存的位置表本身不需要有序** ✓，
> 只需要他按照**产出的顺序注册到一个动态数组**即可 ✓，
> **AST 保存的是他的下标** ✓，以及 **tok 起始位置相对于当前源文件的偏移** ✓
> 也就是**原来 tok 的 `loc` 字段** ✓。**32 位下标加 32 位偏移刚好是 64 位** ✓。
> **位置表的注册没有交错的成分** ✓ —— 宏体复制出来时 ✓，
> **当前的 cpp 上下文正是宏调用的位置** ✓，也就是当**宏体的 tok 真正进入输出流** ✓、
> **被 parser 看到时才真正注册**到位置表 ✓。**他的位置就是宏调用展开处** ✓。
> AST 由于保存了下标 ✓，**输出位置时直接 O(1) 查找** ✓。
> 而所谓的**偏移量本来就不可能是有序的** ✓ —— 一个超大文件中间 include 一个小文件 ✓，
> 偏移量必然是"大—小—大"的过程 ✓；中间如果穿插 `#line` 指令 ✓，
> 那么**行号更可能是任意整数** ✓。**但是数组下标是永远稳定的** ✓。
> 事实上**宏体的 tok 真正进入输出流的那一刻才是他真正的产出时间** ✓。
> 他在源文件的位置 ✓、也就**宏体本身的源位置保存在宏结构里** ✓。
> 也就是对于**需要永续位置表的模式** ✓，解析器 `next` 要求一个 tok ✓，
> 预处理器回填 **tok、tokc 和 loc** ✓，这时候**解析器看到的，就是当前 token 的完整信息** ✓，
> 包括**源文件指针** ✓、**位置诊断文件名** ✓、**诊断行号**等 ✓。
> 如果需要保留 ✓，**直接将其复制到永存的位置表** ✓，**把索引写到 ast 然后推进索引**即可 ✓。

**⇒ 这条纠正了我三轮的错误方向 ✓**：

| 我做的 ✗ | 设计要的 ✓ |
|---|---|
| 用 `tok_index`（arena 字节偏移）当键 ✗，再**二分**找 ✓ | **键就是产出序号** ✓ —— 注册是**顺序**的 ✓，**下标稳定** ✓ |
| 为此写哈希表 ✗（本轮正要落地 ✓）| **不需要查找** ✓：`next` 把**索引一并交出去** ✓ ⇒ O(1) ✓ |
| 把"偏移有序"当成前提 ✗ | **偏移天生无序** ✓（include ✓ `#line` ✓）—— 只有**下标**稳定 ✓ |

**⇒ 关键洞见（用户那句 ✓）**：**"宏体的 tok 真正进入输出流的那一刻才是他真正的产出时间"** ✓
⇒ 于是**注册顺序 = parser 看到它们的顺序** ✓ ⇒ **下标 = 交给解析器的序号** ✓
⇒ 而**位置**是"**当前 cpp 上下文**"（= 宏调用展开处 ✓）✓ ——
这正是 `origin` 链要表达的同一件事 ✓（§8lj ✓），只是现在**在产出时就定下来** ✓。

**⇒ 对 `Node` 的直接后果 ✓**：`Node` 槽位 1 的 32 位可以放**下标** ✓，
而**偏移**（原 `tok->loc` ✓）放在**紧邻的另一个 32 位** ✓ ⇒ **合计 64 位** ✓
⇒ 这样"节点自己**带偏移**" ✓（同一行内多节点的区分 ✓ = 列号 ✓）而"**表按下标 O(1) 查**" ✓
⇒ **列号偏移的问题从根上消失** ✓（偏移是原文精确值 ✓）✓。

### 11.10 往"单语句体"里插入东西：**并入同一条语句**（用户定 ✓）

### 11.11 折叠的两条定性（用户定 ✓）

**设计（照录 ✓）**：

> **泛型表达式只需要对应表达式的类型** ✓，
> **关联表达式不需要立即折叠** ✓、**也没必要折叠** ✓。
> 而是**在解析完成、确定到对应表达式时** ✓，
> **对最后被选中的表达式做折叠** ✓。

> **如果影响了，那就是折叠错误** ✗，**而不是折叠时机的问题** ✗。

**⇒ 这两条纠正了我 §8ne 的诊断 ✗**：

| 我写的 ✗ | 用户定的 ✓ |
|---|---|
| "`fold_node` 依赖解析后才存在的状态" ✗ ⇒ 需要"解析期安全的折叠函数" ✗ | **折叠不改变类型与值** ✓ ⇒ 若变了，**是折叠的 bug** ✗，与时机无关 ✓ |
| "`_Generic` 关联类型此时未定 ⇒ 折得太早" ✗ | **`_Generic` 只要控制表达式的类型** ✓；关联表达式**当时不必折** ✓ ⇒ 选中之后**折被选中的那个** ✓ |

**⇒ 对实现的直接后果 ✓**：
① **不窄化守卫** ✗（我三次收窄都是**治错了病** ✗）⇒ 应当**修折叠** ✓；
② `_Generic` 处要加的是"**选中之后折被选中的那个表达式**" ✓（一处 ✓）；
③ **幂等性** ✓ 可以被**断言** ✓（折两次 = 折一次 ✓）—— 这是一条**便宜且强**的自检 ✓。

### 11.13 死代码消除的**标签粒度**（用户定 ✓，落点已查明 ✓）

### 11.14 标签粒度：**实现与实测** ✓（§11.13 的落地 ✓，含**两处有意偏离** ✓）

* 解析器维护**当前块链** `blk_stack[64]` / `blk_depth` ✓（`compound_stmt2` 压/弹 ✓）；

② 标记**扩到 `case` / `default`** ✓ —— `switch` 的派发与 `goto` 一样从**区域外**跳进来 ✓；
   `87_dead_code` 后半段正靠这一条才通过 ✓（该文件自己也把它写成第二条检查 ✓）。

**⇒ 为什么必须是"注册时"的标记** ✓（这是本次修复的**要害** ✓）：

标签的块号在**解析期**就分配 ✓，而块只在标签**被生成**时存在 ✓
⇒ **丢掉含标签的区域 ⇒ 指向它的边全部悬空** ✓ ⇒ LLVM `use of undefined value` ✓。
而**函数级**的 `fn_has_labels` 只有**折叠完整函数**时才设 ✓，
**交付点折叠却在解析期**进行 ✓ ⇒ 那时读到的是**上一个函数**的残留值 ✗
⇒ 解析期的折叠**完全没看标签** ✓（实测：`87_dead_code` 与最小例 ✓）。
**注册即标记**把答案放在"用得到的时候已经知道"的位置 ✓ ⇒ 解析期与末遍**同一判据** ✓。

**⇒ 仍然保留的边界** ✓（用户定：更高精度留到 IR ✓）：
区域内**有**标签就**保守保留** ✓，哪怕引用它的 `goto` 就在同一区域内 ✓
（`kb_wait_1` 的三目另一支 ✓）—— 只是多几条无用跳转 ✓，语义不变 ✓；
跨语句、跨基本块的精确判定留给 **IR 优化阶段**的完整控制流分析 ✓。
